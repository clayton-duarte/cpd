# cpd 2: implementing

Read this first, then [contract.md](contract.md), [commands.md](commands.md) and [CONTEXT.md](../CONTEXT.md), which are normative. This file only says where things go in the code.

## The one-area rule

Each Job edits **only its own area** (`core/src/<area>/`, `engine/src/<area>/` for `watch` and `doctor`, or `tui/src/` for the cockpit) **plus its tests** (`cli/tests/<binary>/<area>*.rs`, where `<binary>` is the one the area table under Tests gives the area). It does not edit `core/src/lib.rs`, `cli/src/cli.rs`, the shared modules (`core/src/error.rs`, `output.rs`, `ids.rs`, `args.rs`, `home.rs`), `cli/tests/common/`, another area's tests, another area, any `Cargo.toml` or `Cargo.lock`. This is how parallel Jobs merge without conflicts. Need a change outside your area: ask the Lead (`cpd ask`), don't make it.

Within your area you may add files (`<crate>/src/<area>/foo.rs`, declared in your `mod.rs`) and use any other area's public items once that area has landed.

## Layout

- `Cargo.toml`: the workspace, with four members (edition 2024). Dependencies point one way: `cli` depends on `core`, `engine` and `tui`; `engine` depends on `core`; `tui` depends on `core`; `core` depends on none. `tui` does not depend on `engine` (docs/research/workspace-split.md §5.1, part B; this amends hs-d18, "cpd's code is three crates").

| Directory | Package (library / binary) | Holds |
|---|---|---|
| `core/` | `cpd-core` (library `cpd_core`) | every area of the module map below except `tui`, `watch` and `doctor`, and the shared modules (`args`, `error`, `home`, `ids`, `output`). `core/src/lib.rs` is the crate root: it declares every module, once. |
| `engine/` | `cpd-engine` (library `cpd_engine`) | the engine and the health check: the areas `watch` (`watch`, engine steps E1–E15, commands.md §12) and `doctor` (`doctor`, §14.1), in `engine/src/watch/` and `engine/src/doctor/`. It depends on `cpd-core` and uses its public items (the store, events, config, host, session and the shared modules). `engine/src/lib.rs` is its crate root. |
| `tui/` | `cpd-tui` (library `cpd_tui`) | the whole cockpit (`tui`, `tui view`, commands.md §13): `tui/src/lib.rs`, the views and the read model (`tui/src/read/`). It uses `cpd_core` for the store, events, host and the shared modules. It does not depend on `cpd-engine`. |
| `cli/` | `cpd` (binary `cpd`) | `cli/src/main.rs`, which only calls `main_with`, and `cli/src/cli.rs`: the root `Command` enum, `run` and `main_with`. Also `cli/tests/`, the binary-driven integration tests: one test binary per area, `cli/tests/<area>/` (the area table under Tests). |

**The command runner.** The cockpit runs commands in-process (a click runs `session open`, the new-Plan key runs `plan new`) through the root command tree, which `cli` owns and `tui` cannot name (`tui` does not depend on `cli`). So `cli` passes the runner to the cockpit explicitly: `cpd_tui::run` takes a function `fn(Vec<OsString>) -> Result<Output, CpdError>` (`cli::run`), and the cockpit calls it wherever it runs a command. `Output` and `CpdError` are `cpd_core`'s.

**The engine restart.** The cockpit restarts the engine (`watch::restart`), which `cpd-engine` owns and `cpd-tui` cannot name (`tui` does not depend on `engine`). So `cli` passes `restart` to the cockpit as it passes the command runner: `cpd_tui::run` takes it as an argument, and the cockpit calls it wherever it restarts the engine.

## The command tree

`cli/src/cli.rs` holds the root `Command` enum; each variant delegates to its area (`cpd_core::context::run(cmd)`, `cpd_engine::watch::run(args)`, …, and `cpd_tui` for the cockpit). Each area owns its subcommand enum and its argument types. Every command of commands.md §2 is implemented, and `cli/tests/tooling/interface.rs` keeps docs/interface.md, the index of commands.md §2, equal to `cpd --help`'s tree, both ways, and every command in `cli/src/interface.rs`'s table.

To add a command:
1. In your module, define its arguments as a `#[derive(clap::Args)]` struct, and name it from the root or the area's subcommand enum (`watch::Args`, `config::ConfigArgs`, `driver::RunArgs`, …).
2. Make `run` return `Ok(Output::success(json!({…})))` or `Err(CpdError::…)`.
3. Test it in your own test file.

Parsing:
- `--help` and `--version` print one JSON value too: `{"ok": true, "help": "<text>"}` and `{"ok": true, "version": "…", "schema": 1000, "store_schema": <1000, 1001 or null>, "protocol": <P>, "store": <the verdict or null>}`. `store` is what `store::verdict` answers (contract §4.5, commands.md §1.2): `{"opens", "refusal", "unknown", "pending"}`, from `$CPD_HOME`'s database opened read-only, without migrating and without the schema check (`null` when the file does not exist). `schema` and `store_schema` are only the projection the integer-era guards still read (always `1000`; `null`, `1000` when the store opens, `1001` when not) and go away in a later change (hs-d178 D1). No guard compares numbers: they read `store`. `--version` never creates, migrates or writes the database.
- Every clap failure is `usage` (exit 2) with clap's text in `details.help`, except a value that failed one of our own `FromStr` types (ids, `Text`, `Name`), which keeps that type's code (`invalid_plan_id`, `invalid_name`, …). So parse ids by typing the field (`plan: PlanId`), not by validating strings later.

## Output and errors

- **`output::Output`** (`core/src/output.rs`): `Output::success(json!({…}))` prints `{"ok": true, …fields}`, with `"ok"` first. `Output::Owned` prints nothing and exits 0: only for the commands that write their own stdout or own their terminal (commands.md §1.2, amendment 10): `events follow`, `session run`, `tui view`, `tui --attach`. Their failures before taking the terminal are still returned as `Err`. `output::to_line` is one JSON value plus a newline, for `events follow`'s lines.
- **`error::CpdError`** (`core/src/error.rs`): `CpdError::new(ErrorCode::CasLost, "One sentence.").with("attempt", id.to_string())`. Printed as `{"ok": false, "error": {"code", "message", "details"}}`; `details` is always an object. `to_json()` gives the `error` object alone, the shape of an `error` Event's data (add `source` there).
- **`error::ErrorCode`**: every code of contract.md and commands.md, each with its exit code (`Exit`: 1 failure, 2 usage, 3 refused, 4 not found, 5 timeout). A code cannot be printed with the wrong exit.
- **Adding an error code:** the documents name every code; use those. If you truly need a new one, ask the Lead first: it is an amendment to the contract, and `core/src/error.rs` is shared. The change is one line in the `error_codes!` list, under its exit code.

## Migrations

The schema changes by named migrations (contract §4.5; design `docs/research/migrations.md` as amended by hs-d178). To add one:
1. `scripts/new-migration.sh <slug> additive|breaking` (a thin script: it keeps only what must exist before cpd does and runs `exec cpd` for the rest) writes `core/src/store/migrations/<YYYYMMDDTHHMM>-<slug>.sql` with its header (UTC minute; a breaking one gets `after <n>`). No shared list is edited: the build step lists the directory. A migration that needs Rust beside its SQL has a `<name>.rs` with `pub fn run`.
2. Write the SQL. **Additive** only when every statement is one of contract §4.5 A1's (new table plus its `history_tables` row, a non-unique index, a trigger on a table it creates, a nullable or constant-default `ADD COLUMN`, an `INSERT` into `event_kinds`, `record_kinds` or `history_tables`). Everything else, and any value old code parses into a closed type (a record kind), is `breaking`. Never create `T_hist_ins`, `T_hist_upd` or `T_no_delete`: the runner generates them (K4).
3. Adding an Event kind is `INSERT INTO event_kinds (name) VALUES ('<kind>');` plus `core/src/events/kind.rs`, `pi/lib/event.ts`, contract §5.2, and `PROTOCOL` raised in both.
4. Run `scripts/repin.sh` to write `SCHEMA_HASH` (contract §4.3; it also resolves a merge conflict on it) and amend contract §4.4 in the same change; `cargo test` fails with the new value when it is stale. The additive, order and orders tests (§4.5) run in the same `cargo test`.
5. A migration file on `main` is never edited or deleted; a breaking migration already on `main` is never renumbered to a newer timestamp. Only a breaking migration the PR itself adds (absent from `origin/main`) may be renumbered to a newer timestamp. A base breaking migration whose `after <n>` no longer holds after a merge of `main` is corrected in place, header-only: its first line (the header) is updated with the new `after <n>`, every other line byte-identical. It is never corrected by a rename. **Freeze:** once a migration is on `origin/main` and a store has applied it, its `after <n>` header is historical and is never recomputed. The reason: the store records the sha256 of the whole migration text, header included (R3), so a recomputed header refuses that store with `migration_changed` (hs-n544). **Check 2 (the exact count):** the exact count `after n == the names that sort before it` is required only for a breaking migration the PR itself adds (one absent from `origin/main`). A breaking migration already on `origin/main` keeps its historical header. **Check 3 (sorts after every name on origin/main):** a breaking migration the PR adds or renames to a name absent from `origin/main` must sort bytewise (LC_ALL=C) after every name on `origin/main`; `scripts/check-migrations-frozen.sh` fetches `origin/main`, lists every migration name, and fails the Gate with `migration_order` naming the migration and every later name if it sorts before any of them. The remedy is `git mv` to a newer timestamp (a name after the newest on main) and `scripts/repin.sh` to recount `after <n>` (O3 already lets the PR do it); then rerun the check. Existing on the frozen set, a breaking migration keeps its position. **Restore exception:** a breaking migration may be renamed to an earlier timestamp (restoring the name a live store applied) when every line but the first (the header) is byte-identical, and the header's `after <n>` is corrected when the restore shifts how many names sort before it; the new count is the number of names that sort before the restored name in the binary's list. Edits, deletes and additive or legacy renames stay refused. The reason: a store records an applied migration only by name, and its floor (the newest breaking name) is its oldest allowed schema; renaming an applied breaking migration to a newer timestamp orphans the applied name (store_too_new).
6. Tests build stores with `TestEnv` (`cli/tests/common/mod.rs`); never touch the real `~/.cpd`. Converting a User's `~/.cpd` is a Lead step with the User's go.


## Tests

Target contract (ADR 0013): tests are in-process, with fakes behind traits for tmux, git, time, processes. Unit tests next to the code; integration tests in cli/tests call the library API through a `Ports` struct of fake implementations.

- **Unit tests** go in the module they test (`#[cfg(test)] mod tests`), in your area, in `core/`, `engine/` or `tui/`.
- **Integration tests** go in `cli/tests/<area>/<module>.rs` (or `<module>_<topic>.rs`), whichever crate the area is in: today they run the built `cpd` binary; as the migration lands (ADR 0013) they call the library in-process on `Ports`, with everything external faked. There is **one test binary per area**, `cli/tests/<area>/main.rs` (docs/research/workspace-split.md §4.2; docs/research/test-binaries.md): its `mod` lines are the area table below, the one source of truth, and a test checks that every `.rs` under `cli/tests/` (but `common/`) is in exactly one binary. A new file is declared in its area's `main.rs` with `mod <module>;`, and a test's name is `<module>::<test>` in the binary `cpd::<area>`. A file starts with `use crate::common;` and uses the harness `cli/tests/common/mod.rs` (each `main.rs` has `#[path = "../common/mod.rs"] mod common;`):
  - `TestEnv::new()`: a temporary directory with its own `$CPD_HOME` (`cpd_home()`, empty), `$HOME` (`home()`, with a git identity), and `bin/` first on `PATH`; `CPD_*`, `PI_*`, `GIT_*`, `XDG_*`, `TMUX` and `TMUX_PANE` are removed from the environment. The env's directory is made under `TMPDIR` normalised (no trailing `//`: the Gate's `TMPDIR` ends in `/` on a Mac).
  - `env.cpd(&[…])` / `env.cpd_in(cwd, &[…])` run the built binary and return a `Run` (`exit`, `stdout`, `stderr`); `run.json()` asserts exactly one JSON value, `run.ok()` the success envelope, `run.error()` the failure's `error` object.
  - **`Fx` or `TestEnv::cpd`.** `common::fx::Fx::new()` (`cli/tests/common/fx.rs`) is a `TestEnv` whose `fx.cpd(&[…])` / `fx.cpd_in(cwd, &[…])` / `fx.cpd_with(cwd, &[…], vars)` run the command tree in the test process (`cpd::main_with`), with the same `Run`, instead of an exec: use it for every test whose commands start no process of their own (a store, config, policy or read command; the fixtures are `fx.env`, a `TestEnv::bare()` that starts no reaper). Keep `env.cpd` (the binary) for a command that runs the recorded executable again (`pr poll`, `attempt run`, `session reload`, `watch`, a detached driver), for `slot` (it exits the process), for a signal, a terminal or `events follow`, and for a command that owns its stdout with `print!` (`context pending --markdown`): `Fx::cpd` panics on it, as it reads nothing from the writer; a test may call both (`fx.env.cpd`). `Fx` holds a process-wide lock for its whole life (two never overlap under `cargo test`'s threads), sets the env's variables once and puts the environment and the directory back when it drops; `cpd_with` and `cpd_in` set theirs around the one call. `Run::stderr` is empty: a test that reads stderr keeps `env.cpd`. A file is migrated whole, from `env.cpd` to `fx.cpd`, and the old test is removed in the commit that has its replacement green (no test is deleted for being slow).
  - `env.git_repo("name")`: a repo on `main` with one commit; `env.git(dir, &[…])`.
  - `env.tmux_tmpdir()`: the directory where the env's tmux server keeps its socket, `<root>/tmux` when `<canonical root>/tmux/tmux-<uid>/<socket>` is at most 100 characters, the socket name measured with room for the sockets a test derives from it (`DERIVED_SOCKET_ROOM`, 20 characters), else `/tmp` (where the socket is `/tmp/tmux-<uid>/<socket>`), because macOS limits a unix socket path to 104 bytes (`sun_path`) and tmux resolves `/var` to `/private/var`; the teardown removes the socket file (never the directory, tmux's and shared); every test takes the directory from `tmux_tmpdir()`, never from `root().join("tmux")`.
  - `env.tmux(&[…])` and `env.tmux_socket()`: a private tmux server (own `TMUX_TMPDIR` via `tmux_tmpdir()` and socket name, killed when the `TestEnv` drops). Put the socket name in the test's `config.toml` as `tmux.socket`.
  - `env.fake_pi(body)`, `env.fake_gh(body)`, `env.fake(name, body)`: shell scripts on `PATH` that record their argv (`env.calls("pi")`) and then run `body`. The env's `.gitconfig` turns git's automatic maintenance off (`maintenance.auto` false, `gc.auto` 0): git's detached `maintenance run --auto` prunes the fake worktree admin dirs some tests build.
  - `env.command(program)`: any other program in the same environment; also removes `ZDOTDIR` (a User's zsh config rewrites PATH in a tmux pane and puts the real pi before the env's `bin/`), next to the other removed variables.
  - `TestEnv::kill_tmux_server()` (§3.4 A3, hs-d519): `tmux set-hook -gu pane-died` and `-gu window-unlinked` before `kill-server` to disarm the supervising hooks (§6.1) before killing the server, so they do not restart a new engine after the test kills its own. This is also called first in `TEARDOWN_SH`'s `stop_tmux`, so a test's teardown disarms the hooks that would otherwise fire when the test's server goes away. A test that kills its own server must call this, never a bare `kill-server`.
  - `flock`: macOS ships no `flock` command; where none is on PATH the harness writes a perl `flock` shim into `env.bin()` (`flock [-n|--nonblock] [--no-fork] <file> <command...>`: takes `flock(2)` on the file, runs the command with the lock held, exits 1 at once with `-n` when the lock is held), and `env.flock()` is the program to run (the shim, or `flock` itself on Linux); a test never runs `Command::new("flock")`.
  - **Process group and reaper** (hs-d519): every child process a test starts goes through `env.command`, which spawns it in a process group (on Linux `setsid` via `nix::unistd::setsid`; on macOS `setsid` is not available, so the harness uses perl's `POSIX::setsid` instead) so the test's teardown can reap it (`killpg`). The group keeps a test from leaving a tmux server, a driver or any long-lived process behind when it ends or is killed. On macOS (`uname` is Darwin) `alive` is `kill -0` plus `ps -o stat=` (a Z is dead), and `mine` reads the environment with `ps -E -p <pid>` (an Apple platform binary such as `/bin/sh` or `/bin/sleep` hides its environment from `ps -E`, Context record pro-n8, so `mine` is true for what cpd and tmux start, which is what the reaper stops); the reaper's second stage starts in a session of its own with perl's `POSIX::setsid` instead of the `setsid` command. ### Time in tests

A test never sleeps, polls on the wall clock, or measures real elapsed time (no `thread::sleep`, no `Instant::now()` bound); it runs the product's timer on virtual time. `host::limit::limit(name, default)` (CPD_TEST_<NAME>, debug builds) stays only for what a built binary alone can reach, until PR final.

Decided API: in `core/src/clock.rs` (cpd-core, always compiled, no feature):
```rust
pub trait Clock: Send + Sync {
    fn now(&self) -> std::time::Instant;
    fn sleep(&self, d: std::time::Duration);
}

pub struct SystemClock;  // Instant::now, thread::sleep

pub struct ManualClock {
    fn new() -> Self;
    fn advance(&self, d: Duration);
    fn elapsed(&self) -> Duration;
    fn naps(&self) -> Vec<Duration>;
}  // Clone shares one state; now() is construction Instant + virtual elapsed; sleep(d) records d, advances by d, returns at once
```
The Clock trait lives in core, not behind a feature, so core, engine and tui unit tests use it. A timer is passed as `&dyn Clock` (later `Ports::clock`) at the entry of the loop that waits, never a global. Every existing public signature stays: the Clock-taking form is added beside it (`<name>_with(clock, ...)`) and the old one calls it with `&SystemClock`, so no caller changes and behaviour is identical.

A ManualClock is for waits that END BY TIME (a deadline, a back-off, a nap count). A loop whose condition is changed by something outside the test (a real child process exiting, a file another process writes) must not run on a ManualClock: its virtual naps would burn the whole deadline before the event happens; such a loop is tested after its ports exist (PRs port-run, port-tmux, ports), where the event is an in-memory state change.

### Processes in tests

A test never starts a process: `tmux`, `git`, `gh`, `node`, the secret tool and `cpd` are scripted on a `FakeRunner`, whose time is the `ManualClock`. There is ONE process trait, `Runner`; tmux and git are not traits of their own, they are routes of the `FakeRunner` (see ADR 0013).

The real-process ratchet (`no_test_starts_a_real_process_beyond_the_debt`, pro-d314; see The guard, below) is what keeps this target from sliding while ADR 0013's deletion of the real-process sites (`docs/adr/0013-tests-in-process.md`, "What dies in mig-final") stays open: it pins the sites each file has today and fails a new one. It deletes none of them; that deletion is still open.

Decided API, in `core/src/host/runner.rs` (cpd-core, always compiled, no feature, like `Clock`):
```rust
pub trait Runner: Send + Sync {
    /// Runs `cmd` for at most `deadline`; returns what `deadline::output` returns:
    /// the same `Output`, `Failed::Io` or `Failed::Timeout(tool_timeout)`.
    fn output(&self, cmd: &mut Command, tool: &str, deadline: Duration) -> Result<Output, Failed>;
}
pub struct SystemRunner;                      // `deadline::output(cmd, tool, deadline)`; nothing else
#[derive(Clone)] pub struct FakeRunner { .. } // Arc inside: a clone shares the script and the record
impl FakeRunner {
    pub fn new(clock: ManualClock) -> FakeRunner;   // `Reply::takes` passes virtual time on this clock
    pub fn on(self, program: &str, matches: impl Fn(&Call) -> bool + Send + Sync + 'static, reply: Reply) -> FakeRunner;
    pub fn once(self, /* same */) -> FakeRunner;    // used up after one answer
    pub fn route(self, program: &str, handler: Arc<dyn Handler>) -> FakeRunner;
    pub fn calls(&self) -> Vec<Call>;               // every call in order, answered or not
    pub fn unscripted(&self) -> Vec<Call>;          // the calls no rule matched
}
pub trait Handler: Send + Sync { fn handle(&self, call: &Call) -> Reply; }
pub struct Call { pub tool: String, pub program: String, pub args: Vec<String>,
    pub envs: Vec<(String, Option<String>)> /* Command::get_envs: None = removed */,
    pub cwd: Option<PathBuf>, pub deadline: Duration,
    pub stdin: Option<Vec<u8>> /* bytes a writer thread writes to the child's stdin, as secret/op.rs does */,
    pub stderr_to: Option<PathBuf> /* the child's stderr goes to this file, as distill does for pi */ }
pub enum Reply { Exit { code: i32, stdout: Vec<u8>, stderr: Vec<u8>, takes: Duration }, Io(std::io::ErrorKind) }
impl Reply { pub fn ok(stdout: &str) -> Reply; pub fn exit(code: i32, stdout: &str, stderr: &str) -> Reply;
             pub fn io(kind: ErrorKind) -> Reply; pub fn takes(self, d: Duration) -> Reply; }
```

Semantics:
- `on` and `once` rules are tried in order; the first match answers. `program` is compared with the program's file name (`/x/bin/tmux` is `tmux`). A `once` rule is used up after one answer, then the next matching rule answers.
- A call no rule matches is answered by the `route` of its program (a `Handler`, whose `Reply` is treated like a scripted one); else it is `Failed::Io(ErrorKind::NotFound)` (a program that does not exist) and `unscripted()` lists it. A call answered by a rule or a route is not unscripted.
- A reply that `takes` d: if `d >= deadline` the fake does `clock.sleep(deadline)` and returns `Failed::Timeout(e)`, where `e` is built by the same function `deadline::output` uses (`deadline::timeout`): the same `tool_timeout` code, `details.tool`, `details.argv`, `details.deadline_seconds`; else it does `clock.sleep(d)` and returns the `Output` (`ExitStatus::from_raw(code << 8)`).
- The fake never reads `CPD_TEST_DEADLINE_*` and never starts a process. `Call.stdin` and `Call.stderr_to` carry what a caller feeds the child and where its stderr goes: `FakeRunner` records both in `calls()` and a `Handler` can read them (it may write the `stderr_to` file itself). A hung tool is `Reply::takes(d)` with `d` over the deadline: no sleep.
- Callers that go through the `Runner` (`stdin` and `stderr_to` included): `pr/gh.rs run_timed` (29 callers), `context/distill.rs` (`pi` with `stderr_to`, and `git grep`), `session/retitle.rs`, `host/exe.rs asks_to_open_store`, `plan/lock.rs ensure_watch`, `inbox/cmd.rs local_offset`, `git/hooks/exec.rs`, tui `tree/actions.rs`, tui `widgets/host.rs`, tui `widgets/mod.rs hostname`, and engine `watch/restart.rs rebuild_cockpit`.
- Hooks (`git/hooks/exec.rs`): one `Runner` call per hook (`sh -c <hook>`, the context on `stdin`); the hooks of a block still run in parallel, one thread each; the output of a hook reaches the caller when the hook ends, not line by line (a change from before).

Threading: each caller keeps its public signature and has a `_with(runner: &dyn Runner, ..)` form (`git::run::run_with`, `inbox::team`, `secret::op`, `config::catalog`, `doctor::tools`, `watch::pr`, `watch::team`), the old one calling it with `&SystemRunner`. `Tmux` has a field `runner: Arc<dyn Runner>`, `SystemRunner` by default, and `Tmux::with_runner(self, Arc<dyn Runner>) -> Tmux`. No global, thread-local or env var picks a runner. Behaviour with `SystemRunner` is identical.

Where the fakes live: `core/src/fakes` behind the cargo feature `fakes` of cpd-core (off by default; `cpd-engine`, `cpd-tui` and `cpd` enable it in `[dev-dependencies]`). The in-process fake tmux and fake git are handlers there that take what a `Command` carries, routed as `tmux` and `git`; PRs port-tmux and port-git fill it. `FakeRunner` itself is not behind the feature.

- **The guard (the tripwire, allowlist and static sleep check).** The Gate's last segment runs tests through a tripwire that denies real tmux until a test is migrated to the fake. Three mechanisms enforce this:
  - **The tripwire** `scripts/tripwire/tmux` (POSIX shell, passes `scripts/check-portable.sh`, no `timeout`): it takes its program name from `$0` and its allowlist from `allow.txt` next to it (or `allow-<program>.txt` for any other program such as `git`); where it runs from does not matter: a test may copy or wrap the `tmux` it finds on PATH (`bare.rs` copies it as the "older" server), and a copy with no allowlist beside it takes the first PATH directory that has the allowlist and a `tmux`. It starts no subshell and no external command before its verdict (a test makes hundreds of calls). It reads the nextest environment variables `NEXTEST_BINARY_ID` and `NEXTEST_TEST_NAME`; when the pair matches a line of the allowlist it execs the real program (the first one in the PATH entries *behind* the tripwire's directory, so a fake `tmux` in front of it that execs the tripwire is never found again; the program itself gets the PATH it was given, so what it starts meets the tripwire too); otherwise it prints `tripwire: real tmux called by <binary id> <test name>: tmux <argv>` on stderr, appends that line to `${TMPDIR:-/tmp}/tripwire.log` and exits 127. With no nextest variables set it denies all access: a test that builds its own environment (`env -i`, `env_clear`) passes `NEXTEST_BINARY_ID`, `NEXTEST_TEST_NAME` and `TMPDIR` on (`common::tripwire_env_words()`), or its calls are unidentified and denied. A test on the in-process fake tmux (see The fake tmux) never reaches the tripwire. `scripts/gate-run.sh`'s `finish()` function prints the log and fails the run when it is non-empty, so a test that swallows the exit 127 still fails the Gate.

The prefix matches the start of `NEXTEST_TEST_NAME` (a file is a module: binary `cpd::<area>`, name `<module>::<test>`; unit tests: binary `cpd-core`, `cpd-engine` or `cpd-tui`, name = the module path). Shim text (such as `sleep 60` inside a fake's shell body) is not checked: a process the test reaps is allowed.

### Ports, Spawn and run_with

Decided API (PR ports2), in `core/src/ports.rs` (cpd-core, always compiled; `Fakes` behind the cargo feature `fakes`). Present tense for what PR ports2 creates; where the merged code differs from this text, the merged code wins.
```rust
#[derive(Clone)]
pub struct Ports { pub clock: Arc<dyn Clock>, pub runner: Arc<dyn Runner>, pub spawn: Arc<dyn Spawn> }
impl Ports { pub fn real() -> Ports }   // SystemClock, SystemRunner, ProcessSpawn
pub struct Fakes { pub ports: Ports, pub clock: Arc<ManualClock>, pub runner: Arc<FakeRunner>, pub spawn: Arc<FakeSpawn> }  // Fakes::new()
pub fn run_with(ports: &Ports, argv: impl IntoIterator<Item = OsString>, out: &mut dyn Write) -> ExitCode
pub fn main_with(argv: impl IntoIterator<Item = OsString>, out: &mut dyn Write) -> ExitCode  // run_with(&Ports::real(), ..)
```
`Ports` holds the three seams a test fakes: time (`Clock`), short processes with an output (`Runner`: tmux, git, gh, pi, node, the secret tool) and long-lived or replacing processes (`Spawn`). It carries no environment (below). `Fakes::new()` builds a `ManualClock`, a `FakeRunner` on that clock and a `FakeSpawn`, and `fakes.ports` is the `Ports` over them; the test keeps the typed handles to script and to read the record.

**`Spawn`** (`core/src/host/spawn.rs`) is what `Runner` is not: a child that outlives the call, is waited for later, is signalled, or replaces the process.
```rust
pub trait Spawn: Send + Sync {
    fn spawn(&self, l: &Launch) -> io::Result<Pid>;               // a detached process or a child; the real one reaps it
    fn try_wait(&self, p: Pid) -> io::Result<Option<ExitStatus>>;
    fn signal(&self, p: Pid, s: Signal) -> io::Result<()>;
    fn alive(&self, p: Pid) -> bool;                              // zombie-aware
    fn exe_of(&self, p: Pid) -> Option<PathBuf>;
    fn cmdline(&self, p: Pid) -> Option<String>;
    fn exec(&self, l: &Launch) -> io::Error;                      // returns only on failure
    fn stream(&self, l: &Launch) -> io::Result<(Pid, Box<dyn BufRead + Send>)>;
    fn self_exe(&self) -> Result<PathBuf, CpdError>;              // the path of cpd's own executable
}
pub struct Launch { program, args, env_set, env_remove, cwd, setsid: bool, stdout_to: Option<PathBuf>, hand_over: Option<RawFd>, idle: bool }
```
`ProcessSpawn` is the real one (`Command`, `setsid`, `kill(2)`, `/proc` or `libproc`, `exec`). `FakeSpawn` starts nothing:
- `spawn` and `stream` hand out pids from a counter and record the `Launch` in a table; `launches()` lists them in order; `signals()` lists every `(pid, signal)`; a TERM or KILL marks the pid exited by that signal.
- `exit(pid, code)` marks a pid exited: `try_wait` then returns the status and `alive` is false. Until then a pid is running, so a held-open driver or wrapper is a pid that has not exited, with no sleep.
- `alive`, `try_wait`, `exe_of` and `cmdline` read the table; `inherited` (the driver's fd 3 hand-over) is recorded in the `Launch`.
- `exec` is recorded and returns `io::Error::other("faked exec")`; the process is not replaced.
- `self_exe` returns the path the test configured.

**A launched `cpd` child is recorded and run by the test** (decided, pro-d35). When the product launches `cpd` (a driver, a poll, `session run`), `FakeSpawn` only records the `Launch`; it never starts it and never routes it to `run_with`, so no second thread puts virtual time under another clock reader. The test reads `launches()` and, when it wants the child's effect, calls `run_with(&ports, argv, out)` itself on its own thread with the argv of the `Launch`, then `exit(pid, code)`. There is no `cpd-fake` binary and no fake binary or script of any kind.

**Ambient ports: `Ports::scope` and `Ports::current`** (decided by the Lead; reversible: a later explicit threading replaces a `Ports::current()` call by call). `Ports::scope(&ports, f) -> R` sets a thread-local `Option<Ports>` for the duration of `f` and restores the previous value on exit, panic included, so scopes nest. `Ports::current() -> Ports` is the scoped ports of this thread, else `Ports::real()`. `cli::run_with` runs the whole parse-and-dispatch inside `Ports::scope`, so a command reaches the ports a test gave it also through the areas that hand none on. The readers are the old-name wrappers (`old_name()` calls `old_name_with(&*Ports::current().runner, ..)`), `Env::open`, `Env::open_home`, `Env::open_home_persistent` and the default `Tmux` handles. **A new wrapper reads `Ports::current()`, never `SystemRunner`, `ProcessSpawn` or `Ports::real()`**: the guard test `ambient_ports_tests::no_product_file_builds_the_real_ports_by_hand` fails on a non-test line that names them outside its allowlist (the definitions and the entries that start the process on the real ports). A thread a command spawns does not see the scope: capture `Ports::current()` before the spawn and `Ports::scope` it inside the thread.

**`_with` convention.** Every existing public signature stays. A function that needs a port gains `<name>_with(&Ports, ..)` (or `(&dyn Clock, ..)`, `(&dyn Runner, ..)` where it needs one) beside it, and the old name calls it with `Ports::real()`. `Env` is the exception: it gains the field `ports` because its sites cannot all change. The `_with` form holds the logic; the old name is one line.

**`Clock::utc()`.** `Clock` also reports the UTC wall time. `SystemClock::utc()` is the system time; `ManualClock::utc()` is a fixed epoch plus the time elapsed on the clock (`advance` and `sleep` move it), so a stamp the product writes (an Event's `at`, a `started_at`) is deterministic and moves with virtual time.

**Why the mains stay three lines.** `cli/src/main.rs` is `host::exe::record_start()`, `catch_signals` (only for `watch`, as today) and `cpd::main_with(args_os, &mut stdout.lock())`. Everything a test can reach is in `run_with`, so the binary has nothing of its own to test; the exec smoke tests (`--help`, `--version`, an unknown command) run the real `cpd` and need no external program.

**The environment is set once, by `Fx`.** `HOME`, `PATH`, `CPD_HOME` and the cwd are read from the process by the product (`env::var`, clap `env =`, `current_dir()`), and `Ports` does not carry them. `Fx` sets them once at the start of a test, behind a process-wide lock (decided, option 1 of the ports research); nextest runs each test in a process of its own, so nothing leaks between tests. A test never calls `set_var` itself.

**Virtual-time loops.** A loop that waits on the clock (`watch`, `events follow`, `ask`, a driver's poll) calls `clock.sleep`, so a test drives it with `ManualClock::advance` and never waits:
- `watch::run(&ports, until)` runs the engine's ticks until `until` says stop, on the test's thread; the test steps it with `ManualClock::advance`, or calls one `Engine::tick`.
- `events follow` and `ask` run through `run_with` on a thread; the test advances the `ManualClock` once per poll and joins the thread. The thread reads only the shared clock, so nothing is a race.
- The engine's poll (E5) runs `<exe> pr poll` through the runner: `Fx::engine_routes_polling` makes that call `run_with` of the `Fx`'s ports on the poll's thread, and `Fx::route_fn("gh", |call| Reply)` is the `gh` it calls. `Fx::watch_gated(step, poll_ended)` runs `poll_ended` once per poll thread, when that thread has exited, after the poll's result was handed to the engine. A test that looks at an upper bound or an exact value of a time the poll decides holds the engine with it: its `step` waits at the engine's nap for what `poll_ended` signals, so the result is on the channel the engine takes it from before the engine's next iteration applies it, and the poll's end and the next poll's due time (`end + pr_poll_seconds`) are the same whatever the thread scheduling. Releasing the engine at the poll's clock read let its virtual time run on while the result was still unsent. A test that only needs a lower bound (a poll never starts sooner than `end + pr_poll_seconds`) reads `ManualClock::elapsed` in the `gh` closure and needs no gate.
- A held-open `attempt run`, `session run`, `context distill` or `pr rebase` is a `FakeRunner` reply that `takes` longer, or a `FakeSpawn` pid that has not exited.

### The fake tmux

The fake tmux is an in-process route of the `FakeRunner`, not a binary: no test reaches it through `PATH` or the environment, and none starts a process for it. The adapter (`core/src/host/tmux.rs`) runs `tmux -u -L <socket> -f /dev/null <args>` with `TMUX_TMPDIR` through its `Runner`; a test gives it a `FakeRunner` that has the route. The `fake-tmux` binary (`cli/src/bin/fake-tmux.rs`) stays until mig-final, which deletes it.

**Where it lives and how a test gets it.** `core/src/fakes/tmux/`, behind the cargo feature `fakes` of cpd-core (off by default; core, engine, tui and `cpd` enable it in `[dev-dependencies]`; `cli/src/fakes` re-exports it as `cpd::fakes::tmux`). `TmuxRoute` is a `Handler` registered on the program `tmux` of a `FakeRunner`; the runner matches the program's file name, so `/x/bin/tmux` and `Tmux::with_program` paths named `tmux` reach it. A test takes it with `FakeRunner::with_tmux()`, which returns the runner with the route registered, and reads state through `FakeTmux`, the handle of the same route (`FakeRunner::tmux()`; a clone shares the state). `Fx` builds both and puts the runner in `Ports`. Hand the runner to the adapter with `Tmux::with_runner`.

**What it models.** The state of a tmux server, in memory: sessions (`$n`), windows (`@n`), panes (`%n`, argv, cwd, environment, dead, dead status), server and pane options (`@cpd_*`), hooks, bindings, buffers, clients, the key log and the seeded screens. Ids count from 0 and are never reused. The state is one SQLite connection in memory (`Connection::open_in_memory()`) per `(TMUX_TMPDIR, socket)` pair, behind a `Mutex`: the `-L` socket and `TMUX_TMPDIR` of the call pick it, so two sockets are two servers. It makes no file and no process, so nothing leaks, and `kill-server` drops it; the next call says `no server running on <TMUX_TMPDIR>/tmux-<uid>/<socket>` (exit 1). Fidelity the adapter depends on: exit 1 is `no` for `has-session`; a missing or empty `TMUX_TMPDIR` is refused with `error creating /tmp/tmux-<uid> (TMUX_TMPDIR is not set)`; the global flags `-u -L -f` are accepted; a `;`-chained argv runs in order; `-P -F '#{window_id} #{pane_id}'` prints `@n %n`; `#{version}` and `-V` answer `tmux 3.6a`, which the adapter accepts (the route answers `-u -V` before it reads any state, so it needs no server).

**How a test asks it.**
- State: `FakeTmux::state(socket)` returns a read-only view of the socket's server (`None` while no server exists) with `panes()`, `pane_env(pane_id)`, `options()`, `keys(pane_id)`, `popups()`, `hooks()`, `sessions()`, `windows()`: plain structs, no process. A test asserts on the view, or on `FakeRunner::calls("tmux")` for the argv the product sent.
- Screens: nothing runs in a pane, so `capture-pane -p` prints the text a test seeded with `FakeTmux::set_screen(pane, text)` (no `-e` escapes). A test of a rendered view renders with `ratatui::TestBackend`, not `capture-pane`.
- Keys: `send-keys` appends a `KeyLog { pane, keys, literal }` entry, read with `state.keys(pane_id)`.
- Popups: `display-popup` records its argv (`state.popups()`) and calls the handler a test set with `FakeTmux::on_popup(|argv| -> Option<String>)`. The handler returns the contents of the outcome file named in the popup command (`--out`); the route writes that file, in the real temp dir the product named, before the call returns, and `dialog::ask_with` reads it. `None` writes no file; with no handler the dialog fails as it does when the user closes it. `display-menu` records its argv and returns 0.
- Clients: `FakeTmux::add_client(name, w, h)` adds a client of that size (what `list-clients` and `#{client_width}` read).
- Hooks and clicks: an event the route itself causes fires the hook inside the same call (`kill-window` and `kill-pane` fire `window-unlinked`); `FakeTmux::pane_exit(pane, status)` marks a pane dead and fires `pane-died`; `FakeTmux::click(range)` fires the `MouseDown1Status` binding.

**`run-shell`.** `run-shell [-b]`, from a call, a hook or a binding, runs in the foreground through the route's nested `Runner` (`Call { program: "/bin/sh", args: ["-c", <command>], cwd, envs }`, status ignored): on the `FakeRunner` it is recorded and answers exit 0, so a test asserts on the command string (`cpd watch --ensure --wait >/dev/null 2>&1`), never on a shell it parsed. The route releases the state lock before it calls the nested runner, so a script that calls the route again does not deadlock. Every other hook command (`if -F`, `respawn-pane`, `select-pane`, `send-keys -M`, `;`) is interpreted in-process.

**Scripted replies.** What `env.fake("tmux", ..)` wrappers were, a decorator is: `FakeRunner::on("tmux", matcher, reply)` and `once` rules are tried first and the route behind them answers what no rule matches (`unscripted`). A test that needs `list-panes` to print `_` for the tabs, or `new-session` to fail, scripts that one argv and leaves the rest to the route. `FakeRunner::calls` replaces `env.calls("tmux")`.

**What it does not do.** Nothing runs in a pane: the argv of a pane is recorded and never started, so no output, no exit and no shell. A test that drives a live TUI by keys or mouse reports does not use `send-keys`; it calls the view's own event handler. It does not render: `STATUS_FORMAT`, `BORDER_FORMAT` and pane geometry are tmux's to compute, so no test asserts them (the live cockpit and `scripts/preview-tui.sh` are the eye check). `attach` records the client and returns 0. It is never compared with a real tmux (no real tmux in any test): it is pinned by its own unit tests in `core/src/fakes/tmux/` and by running every public `Tmux::*` method of the adapter against it.

The real-tmux harness (`env.tmux`, `env.tmux_socket()`, `TestEnv::kill_tmux_server`, `real_tmux()`, the reaper's tmux stop, the Gate leak check's tmux part) stays as it is and is marked `legacy: removed by the last PR of Plan tests-mock`.

### The git route

`git` is not a trait: it is a route of the `FakeRunner` (ADR 0013). `GitRoute` is a `Handler` for the program `git` (`FakeRunner::with_git()`), in `core/src/fakes/git/` (feature `fakes`). A scripted `on`/`once` reply wins over the route (a test that wants `bad object`, a timeout or exit 128); a call neither answers is unscripted. The route never sleeps and takes no virtual time.

**The Universe.** All state is one `Arc<Mutex<Universe>>` (the mutex stands for git's ref lock), pure data, deterministic, no wall time: the objects (one arena for all repos: blobs, flat trees, commits whose time comes from the `Clock` and whose author from the global `user.*`), the repos (refs, per-worktree HEAD, reflogs, multi-valued config with `url.<x>.insteadOf`, worktrees with their `index` and rebase state) and which repo holds which object (`fetch` and `push` copy the closure). A remote is a config URL, resolved after `insteadOf` to another repo of the Universe by path; a URL that resolves to none fails `fetch`/`push`/`ls-remote` with exit 128 `fatal: unable to access '<url>': Could not resolve host`. Revisions: `HEAD`, a full sha, refs in git's DWIM order, `^{commit}`, `^{tree}`, `<rev>:<path>`, `a..b`, `a...b`. Merging is a per-path text three-way merge (both modified, add/add, modify/delete, delete/delete; mode ignored).

**What a test sees on disk.** The working-tree files are real files in the test's temp dir. A repo is `<dir>/.git/`, a real directory (plus `.git/worktrees/<id>/` for a linked worktree); a linked worktree is a directory with a `.git` file (`gitdir: <repo>/.git/worktrees/<id>`); a stopped rebase is `<gitdir>/rebase-merge/orig-head`; `index` is a real file rewritten by rename on every index change, and a test may create `index.lock` to make a round `Busy`. Everything else (objects, refs, packed-refs, config) lives only in the Universe: **no `.git/objects`, `.git/refs` or `.git/config` file exists**, so a test never reads or writes one. Nothing is written outside the test's temp root; no process, no socket, so nothing leaks.

**What it honours.** Global options `-C <dir>` (repeatable), `-c <k>=<v>` for `core.editor`, `sequence.editor`, `core.quotePath`, `core.filesRefLockTimeout`, `core.packedRefsTimeout` and `user.*` (any other key is unsupported), `--no-optional-locks`; the env `GIT_CONFIG_COUNT/KEY/VALUE` and `GIT_CONFIG_GLOBAL`; no `-C` means the call's cwd. `git --version` prints `git version 2.43.0`, the minimum of `doctor/tools.rs`. A directory with no registered worktree above it is exit 128 `fatal: not a git repository (or any of the parent directories): .git`.

**Strict parsing.** Every subcommand has its own argument parser. A flag or subcommand it does not list answers `fake-git: unsupported: <subcommand> [<flag>]` on stderr with exit 1 AND is recorded in the route; exit 1 is also a real answer (`--quiet` miss, `is-ancestor` no), so the test **fails at drop when the recorded list is not empty**: no caller can read it as "no".

**The fixture API.** `Repo` is the handle a test holds: `write(path, text)`, `commit(msg)`, `branch(name)`, `push()`, `bare_origin()` (a bare repo of the Universe wired as `origin`), `keyed()` (the `https://github.com/acme/<x>.git` form). It calls the functions the subcommands call. `Fx`'s `git(dir, args)` keeps its signature and goes through the route.

**Not modelled** (each answers `fake-git: unsupported`): packed objects and `gc`, git's own hooks (a test that needs `post-rewrite` scripts a `rebase` reply that runs it), submodules, `--git-dir`, rename detection, `.gitattributes`, `core.autocrlf`, pushing to a non-bare remote, `rebase -i` and `rebase --onto`, shallow clones, `stash` (the wrapper refuses it anyway), patch-id dedup of applied commits.

**Fidelity.** No test in the Gate runs real git (policy [tests]). The route is pinned by twin scenarios, `fakes::git::twin`, whose expected stdout, stderr and exit code are LITERAL text recorded once from real git 2.43 by hand in a scratch dir (the git version is in a comment beside each literal, in the test files of PR port-git-fixtures-tests under `core/src/fakes/git/`). The Gate never regenerates them. A behaviour of the route that no scenario pins must not exist (delete it or add the scenario); when real git and the route disagree, the route changes.

### The in-process test kit

PR testkit2 adds, on top of `Fx` (PR tk0), what a test needs to run a command that starts a process, waits on time or draws a view, with no exec, no sleep and no real external. Names are those of `TestEnv`, so a migration is a rename; where merged code differs from this text, the code wins.

- **Ports.** `Fx` runs `fx.cpd(..)`, `fx.cpd_in(..)` and `fx.cpd_with(..)` (same signatures, same `Run { exit, stdout, stderr }`) through `run_with(&Fakes ports, argv, out)`, not `cli::run`. The `Fakes` hold a `ManualClock`, a `FakeRunner` and a `FakeSpawn`. The environment (`HOME`, `PATH`, `CPD_HOME`, cwd) is set once at the start of the test, behind the process-wide lock of `Fx` (decided for the unattended run, option 1 of the ports research).
- **Fake programs.** `fx.fake(program, reply)`, `fx.fake_gh(..)`, `fx.fake_pi(..)`, `fx.fake_op(..)` and `fx.fake_node(..)` register a scripted `Reply` on the `FakeRunner` for that program name; no script, binary or `PATH` entry is made. `fx.calls(program)` returns the recorded `Call`s (what `env.calls(..)` read). An unscripted call (no rule and no route) fails the test at drop, unless the test says `fx.allow_unscripted()`.
- **Virtual time.** `fx.advance(d)` advances the `ManualClock` by `d`. `fx.until(cond)` advances it in steps until `cond` holds, bounded by a virtual limit, and fails with the last state when the limit passes. They replace `wait_until`, `poll`, `wait_some` and `wait_screen`; no test sleeps or reads the wall clock (see `Time in tests`).
- **Launched children.** A `cpd` child a command launches (a driver, a poll) is recorded by `FakeSpawn`, never started. The test takes it with `fx.take_launch(i)` and runs it itself with `fx.run_launch(..)`, which calls `run_with`.
- **Screens.** `Screen` and `Keys` are helpers on `ratatui::backend::TestBackend` for the tui views: `Keys` feeds key and mouse events to the view's own handler, `Screen` reads the rendered buffer as text. They replace `capture-pane` and `send-keys`.
- **The scripted pump and the inline reads.** The loops that follow the store (`cpd_tui::plan::show_with`, `cpd_tui::widgets::show_with`) wait in one place, the `Pump`. A test gives them `Feed::scripted(ports.clock.clone(), signals)`: a `Pump::scripted` with no input thread, and no commit watcher (`Feed::watch` is `Ok(None)`; `Waker::commit()` is how a test says the store changed). `wait(until)` answers the next scripted `Signal` (`Input(Event)`, `Commit`, `Read`, `Due`, `InputFailed`) at once; signals sent through the `Waker` come first. With none left and a time to wait for, it advances `ports.clock` (the `ManualClock`) to `until`, never past it, and answers `Due`; with none left and no time, or after 10 000 `Due` in a row, it panics, because a script that does not end the loop is a test that hangs. Neither view has a key that ends it, so the script ends it with `Signal::InputFailed`, and the loop returns `ViewError::Terminal`. The reads and the Worker actions run INLINE for a scripted pump (`Reads::on`, `Background::on`): the job runs in the caller, so it is finished when `request` or `submit` returns and `take` yields it; no reader thread, no race. The loop reads the pump's events, not `ctx.input`. `plan::prepare` and `widgets::prepare` make what the loop starts from, on a `CpdHome` the test passes; `history::show_with` (`cpd_tui::show_history_with`), `logs::show_with`, `widgets::legend::show_with`, `merge::show_with`, `dialog::show_with` and `worker::event_loop_with` take a `Ctx` and `ctx.input` as before. Production calls them with `Feed::real` (the input thread, the `notify` watcher) and `CrosstermInput`.
- **Not in this PR.** The git and tmux fixtures are in `The git and tmux fixtures of Fx`. There is no `cpd-fake` binary and no fake binary or script of any kind. The shell scripts that stay shell (cargo.sh, pnpm-fresh.sh, preview-tui.sh, check-portable.sh, check-migrations-frozen.sh, repin.sh, new-migration.sh, test-time.sh, pi-check.sh, tripwire/) keep the exec tests of their own script: each file is one line of `scripts/tripwire/shell-tests.txt` (`<file> # <reason>`), the named exception list.

## The Gate leak check

(hs-d519, docs/research/hygiene.md). The Gate notes what its own test run creates and fails when any is left at the end; nothing hunts machine-wide. A new `scripts/gate-run.sh '<command…>'`, and `package.json`'s `verify` becomes `scripts/gate-run.sh pnpm run verify:steps` (the present chain moves unchanged to `verify:steps`). The Gate's pre-merge hook (in this repo's policy file, contract §7.3) already runs `pnpm run verify`, so the check runs in every Gate and in `pnpm run verify` by hand, once, after the last step.

**How a run's own leftovers are identified from other runs'.** One random run id, made by the script and inherited by everything the run starts: `RUN=$(mktemp -d "${TMPDIR:-/dev/shm}/gate-run.XXXXXX")`; `GATE_RUN=${RUN##*.}` (6 random characters); `export GATE_RUN TMPDIR=$RUN`. Directories are keyed on that id: `tempfile::tempdir()`, `mktemp` and `scripts/pi-check.sh` honour `TMPDIR` and create entries under it. `ENVS_DIR` in `cli/tests/common/mod.rs:201` becomes `$TMPDIR` when set (else `/dev/shm` as today). At the end, anything under `$RUN` is a leftover. Processes carry the id: every `TestEnv::command` call and tmux server inherit the `GATE_RUN` variable; on Linux the script scans `/proc/[0-9]*/environ` of its own uid for the exact entry `GATE_RUN=<id>` and excludes itself and its ancestors. On macOS there is no /proc, so the run's processes are found with `ps -axww -E -o pid=,command=` (it prints each process's environment after its command), keeping the lines that contain ` GATE_RUN=<id>`. That scan's own `ps`, `grep` and subshell carry the id too, but they have exited when the pids are examined: a pid that is no longer alive (`kill -0` fails) is not a leftover, so a clean run of `true` prints nothing and exits 0 (before the fix: `process N (ppid )` twice, exit 1). **Limit of the macOS scan** (Context record pro-n8, Mac `pro`, Darwin arm64): SIP hides the environment of Apple platform binaries from `ps -E` (`/bin/sh`, `/bin/sleep` and the like), so a leftover of that kind carries `GATE_RUN` but is not found. Processes that are not platform binaries (homebrew tmux, node, python3, `cpd` and every other binary cargo builds, so the test binaries and what they spawn) are listed. The limit is accepted because what the tests leave in practice (tmux servers, cpd, test binaries, node) is visible; Linux reads `/proc/<pid>/environ` and has no such limit. The script, its ancestors and its descendants are still never leftovers. **pro-d155:** a process is also found by `TMPDIR` equal to the run's directory, so a daemon that scrubbed `GATE_RUN` with `env -i` but kept `TMPDIR=<run dir>` is found too (the sccache case of PR #557, where it survived `cpd gate finish` with its TMPDIR deleted). The match is exact equality: the machine-wide sccache server, whose `TMPDIR` is the run's parent directory (`scripts/cargo.sh`, #559), and another run's directory are not leftovers. Not covered: a process whose cwd is inside the run's directory (the Spawn port has no cwd reader), one whose `TMPDIR` is a directory inside the run's directory but not the run's directory itself, and one that cleared both `GATE_RUN` and `TMPDIR`. The macOS SIP limit above applies to the `TMPDIR` scan as well. For tmux sockets, `TestEnv` names them `cpdt-$GATE_RUN-<pid>-<n>`; `pi-check.sh` starts no tmux (it runs pi on a pty), and its processes carry `GATE_RUN` through its `env -i` allow-list.


**The split: `scripts/gate-run.sh` and `cpd gate finish`** (Plan tests-mock, pro-d35). The shell keeps only what must exist before cpd does: `mktemp`, the exports (`GATE_RUN`, `TMPDIR`) and running the command. It then runs `cpd gate finish --run <id> --status <n>` (the cpd that `verify:steps` built), also when the wrapper is cancelled by INT, TERM or HUP (the traps are set before the command starts, which runs in the background; the signal stops it, and `<n>` is 128 plus the signal: 130, 143, 129; a signal before the launch kills nothing and `cpd gate finish` stops what the command left), which does the leftover check, the kill and the report. The check is a function over `Spawn` (`Spawn::with_env(key, value) -> Vec<Pid>` replaces the `/proc/<pid>/environ` and `ps -axww -E` scans) and std `fs` (tmux sockets named with the id, paths under the run's TMPDIR); only what carries the run's id is killed or removed: a process with `GATE_RUN=<id>`, or with `TMPDIR` equal to the run's directory, counted once (pro-d155). The `TMPDIR` match is exact equality, so the sccache server, whose `TMPDIR` is the run's parent directory, is not a leftover. Not covered: a process whose cwd is inside the run's directory (no cwd reader in the Spawn port), one whose `TMPDIR` is a directory inside the run's directory, and one that cleared both `GATE_RUN` and `TMPDIR`. The macOS SIP limit applies to the `TMPDIR` scan too. The report text (`gate-run: FAIL: this run (GATE_RUN=<id>) left N things behind:`, the `process <pid> (ppid <n>) <command>` lines and the NEXTEST_TEST_NAME hint) is unchanged byte for byte, and the exit status stays 64. `package.json` keeps `scripts/gate-run.sh pnpm run verify:steps`, and `pi/test/gate.test.ts` keeps pinning it. **Decision (1): when the build of `verify:steps` failed there is no cpd binary.** The wrapper then removes its run directory, prints nothing, returns the command's status and skips the check: nothing ran, so nothing leaked, and the Gate fails on the build anyway. There is no other exception. The tests of the check run in-process on `Fakes` (cli/tests/tooling/gate_run.rs is replaced by the tests of rs-gate2-tests, assertions kept); the wrapper keeps an exec test of its own script, as a named exception of the shell scripts that stay shell, guarded by `scripts/check-portable.sh`.

**What it prints on failure** (stderr, then exit 1): `gate-run: FAIL: this run (GATE_RUN=aB3dE9) left 3 things behind:`, one line per leftover (process, socket, path), then `gate-run: the test that left them:…`, then `gate-run: stopped 2 process(es) and removed 2 path(s) of this run`. It then `SIGKILL`s only the pids it listed and removes only the listed sockets and `$RUN`, so the failure itself leaks nothing; a clean run prints nothing and removes the empty `$RUN`. A leftover process's hint names a command that exists on the OS: where /proc exists `tr '\0' '\n' </proc/<pid>/environ | grep NEXTEST_TEST_NAME`, on macOS `ps -E -p <pid> -o command= | tr ' ' '\n' | grep NEXTEST_TEST_NAME`. This macOS branch was run on macOS (Darwin arm64) and is no longer unverified. Cite hs-d519 and docs/research/hygiene.md in the docs. **Tests to list** (cli/tests/tooling/gate_run.rs): a clean run of `true` prints nothing, exits 0 and leaves no `gate-run.*` directory; the existing clean-run, process, directory, socket and other-run tests pass on macOS as on Linux, so the harness uses no /proc, no `setsid` and no GNU-only flag; a left process's hint names `/proc/<pid>/environ` where /proc exists and `ps -E -p <pid>` where it does not.

- `scripts/cargo.sh` takes one slot of the policy resource `cargo` (pro-d132) at step level: only while cargo runs, and the slot is released the instant cargo exits. It takes the slot after it has resolved cargo and finished the sccache step, because the sccache server is a long-lived daemon: started after the slot is taken, it would inherit the slot's lock descriptor and keep the slot after cargo exits. Then it decides once: (1) `CPD_CARGO_RESOURCE_HELD` is unset or empty (an empty value counts as not held); (2) `cpd` is on `PATH`; (3) the output of `cpd resource list`, run in the caller's current directory with stderr and exit status ignored, contains the exact text `"name":"cargo"` (cpd prints one compact JSON line, so a host, owner or repo policy that declares `cargo` matches). When all three hold, it runs `export CPD_CARGO_RESOURCE_HELD=1` and then `exec cpd resource run cargo --wait 30 -- "$cargo" "$@"`: cpd takes one free slot, waiting up to 30 minutes, and refuses `resource_busy` (exit 3, cargo never started) when none frees; then it replaces itself with cargo, so cargo keeps the exit status, stdio and signals, and the slot is held as long as cargo and any descendant that keeps its lock descriptor live (commands.md §30.2; the policy is a `[resources.cargo]` table with `slots`, contract §8.3 "The `resources` domain"). Only the mac-pro machine policy declares it, with `slots = 3` (3 runs x 4 rustc jobs, `.cargo/config.toml`, on 14 cores), so every other machine, and every isolated test run, is uncapped. The script is the same either way: a declaration only selects the branch. When any of the three fails (no `cpd` on `PATH`; `cpd resource list` fails for any reason, such as no git worktree, no config or no owner policy; or it lists no `cargo`), the script runs `exec "$cargo" "$@"` as before, silently, with no warning. The cap is therefore lost silently whenever `cpd resource list` fails; that is the accepted trade-off (assumption A1). When the guard is already set, the script does not call `cpd` at all.

## `cpd install`

`scripts/install-cpd.sh` is the bootstrap and nothing more: cpd does not exist yet when it runs. It runs `CPD_COMMIT=$(git rev-parse --short HEAD) scripts/cargo.sh build --release --locked -p cpd` ("The version string" below), then `exec target/release/cpd install --root <checkout>` (`target` is `$CARGO_TARGET_DIR` when set). A failed build stops the script and installs nothing. `scripts/check-portable.sh` keeps guarding the script (contract §6.1); it keeps no `python3`, `find`, `readlink`, tmux or `kill` call.

Everything else is `cpd install --root <checkout>` (commands.md §14.4; `cli/src/install.rs` over `cpd_core`), written in Rust over `Ports` (`Runner` for `git`, the built and the installed `cpd`, `tmux` and `scripts/tag-version.sh`; `Spawn::alive` for a scratch directory's pid; std `fs` for files; `cpd_core::lock` for the engine lock). The steps, in order; a step that fails before step 5 replaces nothing and exits 1:

1. **Preflight.** The adapter path `<link>` (`<share>/pi`, `<share>` = `<dir of the installed binary>/../share/cpd`) is absent, a symlink or a directory; anything else: `cpd install refused: <link> is neither a symlink nor a directory`. (`python3` is no longer a requirement: the message `python3 is required for the atomic adapter swap` is gone with the dependency.)
2. **The migration check** (the branch check, contract §3.7). `git -C <root> fetch --quiet origin main` through the `Runner`; a failed fetch refuses (`cannot fetch origin/main to check that this build's migrations are on it`). For each file of `core/src/store/migrations/` in the checkout, `git cat-file -e origin/main:<path>` and `git show origin/main:<path>` must exist and equal the file; the names that do not are listed: `cpd install refused: this build carries migration <names> that is not on origin/main, and a preview would apply it to <CPD_HOME>/cpd.db before the PR merges. Merge main into this branch, or wait until the PR merges, then install again.` The script has already built the binary when this runs, so the check no longer precedes the build; it still precedes every replacement, and nothing installed changes (the old script refused before it built; the tests keep their names, "refused before building" now means before replacing).
3. **The verdict of the built binary** (the store check, contract §3.7). `<target>/release/cpd --version` through the `Runner`, with the caller's `CPD_HOME`. A `--version` that fails, or whose JSON has no `store` field, is refused (`cpd install refused: <path> --version failed:` / `reports no store verdict:`, then its output). `store.opens` false is refused: `cpd install refused: this build cannot open <CPD_HOME>/cpd.db: <store.refusal.message>` and the fix of `store.refusal.code` (`store_too_new`, `migration_changed`, `migration_order`; any other code prints the message alone). A store that does not exist, or opens, installs: `unknown` additive migrations are no refusal. The verdict is the store's opening: the command never migrates the store (contract §4.5 "The window"); the migration is the new engine's start.
4. **The config migration and validation** (contract §3.7 "The config migration and validation", hs-d721, hs-d722). `<target>/release/cpd config --migrate` through the `Runner`, with the caller's `CPD_HOME`: reads `$CPD_HOME/config.toml`, applies the migrations in order (hs-d722; the two first are `distill-tier-gx` and `drop-test-concurrency`, hs-d722 and hs-d679), validates the result (the same checks as plain `cpd config`, including Tier rules), and writes the file only when it changed and only when the result is valid. On success prints `{"ok":true,"path":"<path>","migrated":["<name>",...]}` on stdout (empty array when nothing changed) and each applied migration as `cpd install: config.toml migrated: <name>` on stderr. Refusals: `config_missing` (the file is absent), `config_invalid` (the migrated file is still invalid, `details.key` names it). The file is untouched on any refusal. The migration happens before the binary is replaced, so that if it fails, the config is not mutated.
4a. **The adapter packages** (contract §3.7 "The adapter packages"; commands.md §14.4 step 4a). Runs after step 4 and before step 5, so a failure leaves the binary, the adapter link and the config as they are. It reads `<root>/package.json`. When the file is absent, or has no `dependencies` key or an empty one, it does nothing and runs no pnpm (today the root package.json has no `dependencies`, so no machine runs pnpm at install). Otherwise `<root>/pnpm-lock.yaml` must exist, else the install is refused: `cpd install refused: package.json has dependencies but the checkout has no pnpm-lock.yaml`. It creates `<share>` (`~/.local/share/cpd`) if needed, copies `package.json`, `pnpm-lock.yaml` and, when present, `pnpm-workspace.yaml` there byte for byte, and runs `pnpm install --prod --frozen-lockfile` with working directory `<share>`, bounded at 10 minutes, output captured. A non-zero exit, a timeout, or a pnpm that cannot start (not installed) refuses the install: `cpd install refused: pnpm install --prod --frozen-lockfile failed in <share>:` then the captured stdout and stderr, trimmed (for a pnpm that cannot start, the error). Result: `<share>/node_modules` holds the production packages only (no devDependencies). Idempotent: the same package.json and lockfile give the same result. Its refusals are in commands.md §14.4's table.
5. **The binary.** The built file is copied to `<dest>/.cpd.tmp.<pid>` (`<dest>` = `~/.local/bin`, made when missing), set to mode 755 and `rename`d over `<dest>/cpd`: atomic, also while `cpd` runs. A failure removes the temporary file.
6. **The adapter swap** ("The adapter swap" below), then the verify and the cleanup.
7. `installed <dest>/cpd and <link>` on stderr.
8. **The follow-ups** on the new binary (`<dest>/cpd`, through the `Runner`; "The install's engine order" below): `cpd config`, `cpd watch --check`, `cpd tui --respawn`, `cpd watch --mark-restart`, `tmux -u … kill-window -t =<work>:watch`, `cpd watch --ensure`, and the check that an engine holds `locks/watch.lock` (`cpd_core::lock`, a non-blocking probe of the lock file; `python3` and `flock` are gone).
9. **The tag.** `scripts/tag-version.sh` through the `Runner`, once, after the follow-ups (docs/versioning.md "Tags"). A non-zero exit prints its stderr under `tag-version:` as a warning and does not change the install's exit; a refused or failed install (any step above) never reaches it.
10. **The exit.** 1 when any `cpd install follow-up failed` line was printed, else 0 (the output is human text on stderr, as the script's was; commands.md §14.4).

The tests are in-process on `Fakes` (docs/implementing.md "Tests"): `run_with(&ports, ["cpd","install","--root",<checkout>])` over a temporary `HOME` and `CPD_HOME`, with `Runner` routes for `git` (a `Universe` with `origin/main`), `cpd` (the built one and the installed one, each scripted by its argv), `tmux` (`TmuxRoute`) and `scripts/tag-version.sh` (a call count on the route, replacing the recording script), and `ManualClock` for the lock wait (no sleep). The tests for config migrations (`cpd config --migrate`), the follow-ups (`cpd watch --check`, `cpd tui --respawn`, `cpd watch --ensure`, the lock hold), and the install's full sequence run through `cli/tests/tooling/install.rs`. The 51 tests of `cli/tests/tooling/install_script.rs` keep their names; `cli/tests/tooling/install_script.rs` is replaced by in-process files (Jobs `rs-install2-tests-a` to `-c`), each old test deleted in the commit that adds its replacement, assertions kept. The four portability tests of `install_script.rs` (`check-portable.sh`, which guards the shell that stays) stay an exec test of their own script, a named exception (ADR 0013). One `assert_cmd` smoke test runs the binary's `install --help`.

## The adapter swap

hs-d355 (incident: `renameat2` is Linux-only; on macOS the install script died with `AttributeError: dlsym(RTLD_DEFAULT, renameat2): symbol not found` under `set -eu`, right after the binary swap, so the adapter, the views and the engine stayed old on every Mac). The contract fixes the layout, the rename, the migration, the cleanup and what pi sees (contract §3.7 "The adapter swap"); this section is `cpd install`'s algorithm, from which the tests are written. Linux and macOS run the same code; there is no `cfg(target_os)` branch and no `python3` (unverified on macOS: `std::fs::rename` is `rename(2)`, which replaces a symlink atomically on both; the first Mac install after this change is the proof).

`cpd install`, after the binary is replaced (step 4), with `share=<dir of the binary>/../share/cpd`, `link=$share/pi` and `<pid>` its own `std::process::id()`:

1. **Preflight, before anything is replaced:** `$link` is absent, a symlink or a directory (install step 1).
2. **Build:** `$share/pi.tmp.<pid>` ← a copy of `pi/` minus `test/` (`fs::create_dir`, then a recursive copy of every entry but `test`); then `rename` it to `$share/pi.<id>` with `<id>` = `<UTC YYYYmmddTHHMMSS>-<pid>` (`Clock::utc`, so a test sets it). A version directory therefore exists whole or not at all. A guard removes `pi.tmp.<pid>` and `pi.link.<pid>` when the install returns early.
3. **Link:** `std::os::unix::fs::symlink("pi.<id>", $share/pi.link.<pid>)` (relative target: the tree can be moved or copied).
4. **Swap:** one `fs::rename("$share/pi.link.<pid>", $link)` (`rename(2)`; the same on both platforms). `ln -sfn` and a remove then link are never used: they are not atomic.
   - `$link` absent: step 4 alone, atomic.
   - `$link` a symlink: step 4 alone, atomic. Its previous target (`fs::read_link`, never canonicalised) is the **displaced** version.
   - **`$link` a real directory (the migration, the first install after hs-d355):** `fs::remove_dir_all($share/pi.legacy)` (a stale leftover), then `fs::rename($link, $share/pi.legacy)`, then step 4's rename, back to back in the same process. **Not atomic**: `$link` is missing between the two renames, for microseconds, once per machine (a rename of a symlink over a directory fails `EISDIR`, and no portable call exchanges the two); the window holds no process start-up. If the second rename fails, `$share/pi.legacy` is renamed back to `$link`, the install prints `cpd install failed: cannot swap the adapter link over <link>; the old directory is back` and the error, exit 1. `pi.legacy` is the displaced version.
5. **Verify:** `$link/package.json` exists; else exit 1 `cpd install failed: <link> has no package.json after the swap`.
6. **Clean up** (after the verify; a failure prints `cpd install warning: could not remove every old adapter version under <share>` and does not fail the install). **Pass 1 reads the pins** `$share/pi.pin.<pid>` (written by the adapter at load, below): a pin whose pid `Spawn::alive` reports alive protects the version its target names when that target is a version name (`pi.legacy` or `pi.<digit>…-<digit>…`, the grammar of `is_version`), with no time cap; a pin whose pid is dead, or does not parse, is removed; a live pin whose target is not a version name protects nothing, is never followed, and is removed. **Pass 2** removes each `$share/pi.<id>` and `$share/pi.legacy` that is not the target of `$link` now, is not the displaced version, is not protected by a live pin, and whose modification time is more than 60 minutes before `Clock::now` (std `fs::metadata`, read against the clock, so `ManualClock` ages a directory without a sleep); remove each `$share/pi.tmp.<pid>` and `$share/pi.link.<pid>` whose pid `Spawn::alive` reports dead. The cleanup never touches `$share/node_modules`, `$share/package.json` or `$share/pnpm-lock.yaml`. So, at rest and with no live pin, installs one after another leave the current and the displaced version only; a concurrent install's unlinked version (minutes old at most), its tmp directory and its link (live pid) are never touched.
7. `installed <bin> and <link>` on stderr, as before; then the follow-ups (views, engine) run.

**The packages beside the adapter** (step 4a of the list in `## cpd install`). `$share/node_modules` is installed before the swap by `pnpm install --prod --frozen-lockfile` in `$share`, from copies of `<root>/package.json`, `<root>/pnpm-lock.yaml` and `<root>/pnpm-workspace.yaml`, so it holds the production packages only. Every `pi.<id>` finds them because Node resolves a bare import by walking up from the file's real path: `$share/pi.<id>/...` reaches `$share/node_modules` (verified by the Lead with a plain `node` script through the `pi` symlink; unverified for pi's jiti loader, to be checked by the first Plan that adds a dependency). The step is skipped when the root package.json has no `dependencies`, which is today, so no machine runs pnpm at install.

Two installs at once: each builds its own `pi.<id>` and `pi.link.<pid>` (`<pid>` keeps them apart); the renames serialise in the kernel, the last wins, and the loser's version becomes the winner's displaced version (kept, then cleaned by a later install). The binary's rename is atomic as before.

**The pin** (pro-d224; contract §3.7 "The adapter swap"). `$share/pi.pin.<pid>` is a symlink whose target is the bare name, no slash, of the version directory that the process with that pid loaded the adapter from. The adapter writes it itself, at load, from the real path of its own files, and only when that real directory is a version directory (`pi.legacy` or `pi.<id>`); it never goes through the `pi` link. Nothing writes a pin from a checkout run (`pi/`), from a `pi_adapter` override that is not a `pi.<id>` directory, or from the durable runner, which imports nothing lazily.

What a running pi sees: the path `pi` resolves to the old or the new version, complete, at every instant (except the one-time migration window). A Session started during the swap loads one of them whole. A running process pins the version it runs from (the pin above), so the files it reads later through its real path stay until it ends. No module of the adapter is imported after load by a relative literal specifier: a relative dynamic `import()` is banned in non-test `pi/` sources by `pi/test/ask-user-question/no-lazy-import.test.ts`, because a live pi lost a module it had not imported yet when an install pruned its version (Context pro-d223); ask-user-question imports its submodules statically for that reason. Limits: a pi started before the pin existed pins nothing until it reloads; a pid reused by an unrelated process keeps one version until that process exits (accepted). Its reload poll watches the installed path `pi` (a symlink; `stat` follows it): the identity (`dev:ino:mtimeMs`) changes at the rename, and a missing path stays "not a change" (the migration window). `adapterDir()` in `pi/lib/reload.ts` is `dirname(dirname(import.meta.url))`, which is the real directory `pi.<id>` if Node or pi resolves the link (unverified; the rule does not depend on it), so: **when the directory's name matches `pi.<id>` or `pi.legacy`, the adapter watches its sibling `pi`; otherwise (the checkout's `pi/`, the tests) its own directory.**

The pin's tests, each rule exact:

- `install::adapter_tests::a_version_a_live_pid_pins_survives_two_later_installs_once_it_is_old`: a version older than 60 minutes that a live pid pins is kept by each of two later installs; the pin has no time cap.
- `install::adapter_tests::a_pin_of_a_dead_pid_is_removed_and_the_old_version_it_named_is_swept`: a pin whose pid is dead is removed by the install, and the version it named is then removed in the same install, as today's rule applies to it (old, not current, not displaced).
- `install::adapter_tests::a_pin_that_names_no_pid_is_removed`: a pin whose `<pid>` does not parse is removed.
- `install::adapter_tests::a_pin_naming_something_that_is_not_a_version_is_removed_and_never_followed`: a live pin whose target is not a version name protects nothing, is removed, and its target is never followed.
- `pi/test/adapter-pin.test.ts`: the adapter writes `pi.pin.<pid>` at load, its target the bare name of its own version directory, and writes nothing from a checkout run, a `pi_adapter` override that is not a `pi.<id>` directory, or the durable runner.
- `pi/test/ask-user-question/no-lazy-import.test.ts`: no non-test `pi/` source contains a relative dynamic `import()`.

The tests run `cpd install` in-process on a temporary `HOME` with: no `pi`; a `pi` symlink; a real `pi/` directory (the migration: `pi` is a symlink to a complete `pi.<id>` afterwards, `pi.legacy` holds the old files; a failing step 4, a rename the test makes fail by a read-only `share/`, restores `pi/`); a regular file (refused, nothing replaced); two installs one after another (only the current and the displaced version remain); a live-pid `pi.tmp.<pid>` (kept: `FakeSpawn` says the pid is alive) and a dead one (removed); a version modified a minute ago (kept; `ManualClock`), and one modified two hours before (removed); and, for the adapter, `adapterDir()` and the reload identity over a temporary `share/` with a `pi.<id>` and a `pi` link swapped by `rename`, in `pi/test`. The `python3` cases (a `python3` without `renameat2`, a missing `python3`, a `python3` whose `os.replace` fails) have no counterpart: the dependency is gone, and the test names that carried it keep their other assertions. A process that polls `pi/package.json` during a symlink swap never sees it missing; during the migration it sees it missing in a tiny fraction of its polls (the window is two renames of one process, not a process start-up).

## The install's engine order

hs-d463 (incident: mac-pro's first sync install after #169 killed `cpd-work:watch`, then `cpd tui --respawn` and `cpd watch --ensure` both failed `tmux_failed`, and the engine stayed down for hours). The contract fixes the rules (§3.7 "The install's engine order", §6.1 "Every tmux call is a UTF-8 client"); this section is `cpd install`'s order (install step 7) and its tests, from which the failing tests are written.

**`cpd install` after the binary and the adapter swap** (`<dest>/cpd` is the new binary; the running engine is the old image):

1. `cpd config`. Fails: print `cpd install follow-up failed: cpd config: <message>; the engine was not touched: the engine that runs, if one does, is the old one and keeps running; the views were not respawned`; go to the exit (steps 2 to 4 are skipped, they need the config).
2. `cpd watch --check` (new; commands.md §12 gains it). Fails: `cpd install follow-up failed: cpd watch --check: <message> (<code>); the engine was not touched: …` as above; **no `tmux … kill-window` is run**; go to the exit.
3. When the cockpit has its `main` window: `cpd tui --respawn`. Fails: `cpd install follow-up failed: cpd tui --respawn exited <code>: <message>; the views still run the old binary`; continue.
4. When the work session has its `watch` window: mark (`cpd watch --mark-restart`, hs-d471: it writes `run/install-restart.json`, contract §3.7 "A planned restart"; a failure prints `cpd install follow-up failed: cpd watch --mark-restart: <message>; the engine restart is not marked as planned` and the retirement goes on), retire (`kill-window`, then check if the window is gone; if it is, the engine had already left by standing down (A1, above) and it is no failure; if still there, it fails as before; then wait for `locks/watch.lock` free, 0.25 s steps, at most `CPD_INSTALL_LOCK_WAIT_SECS`), start (`cpd watch --ensure` once), check (the lock is held). The three failures and their texts are in the contract's table; each failure after the `kill-window` says `the old engine was stopped and no engine is running`.
5. Exit 1 when any `cpd install follow-up failed` line was printed, else 0. The `tmux` calls go through the `Runner` as `tmux -u -L <socket> -f /dev/null …` with `TMUX` and `TMUX_PANE` removed (`host::tmux::client`); the wait for the lock reads `cpd_core::lock` and waits on `Clock::sleep` (0.25 s steps), so a test advances `ManualClock` and never sleeps.

**`cpd watch --check`**, what it verifies and in which order (contract §3.7 step 1): config, the store's read-only verdict (`store::verdict` on a read-only open: refusal codes of contract §4.5, pending migrations known to this binary; it never migrates and writes no database file, WAL or `locks/store.lock`; the migration is the new engine's start, after the old one is retired), `tmux -V` >= 3.6, the tmux listing parsed (`list-panes -a -F` with the liveness format; skipped when no server runs), the home's `locks/` and `run/` (tested, not made) and the probe of `locks/watch.lock` (opened only if it exists, no create, no `flock`). It writes nothing at all. The test for each: a fixture that breaks exactly that thing (a config that does not parse; a store with a newer `user_version`; a fake `tmux` printing `_` for the tabs; a `CPD_HOME` under a read-only directory) makes `watch --check` fail with that step's code, and the same fixture makes `watch --ensure` fail the same way, so the check cannot pass what the start would fail.

**`cpd tui --respawn`** runs checks (a), (b) and (d) before its first `respawn-pane -k`; the test is the fake tmux that prints `_` for the tabs: no `respawn-pane` is run, the command fails `tmux_failed`.

**The tests** (`cpd install` in-process on a temporary `HOME` and `CPD_HOME`, with a `cpd` route for `<dest>/cpd` and the `FakeTmux` route, both logging their calls in order; the same harness as the adapter swap's):

## The portability check

hs-d355: the scripts Macs run are checked by `scripts/check-portable.sh`, which the Gate runs (`pnpm run verify`), so a Linux-only call fails on hs and not on a Mac. Usage: `scripts/check-portable.sh [<file>...]`; with no argument it checks the covered list below, with files it checks exactly those (the tests feed it fixtures). On success: `check-portable: ok (<n> files, <m> exempt)` and exit 0. On failure: one line per hit on stderr, `<file>:<line>: <pattern>: use <alternative>`, a last line `check-portable: FAIL (<k> hits)`, exit 1. It needs only `sh`, `grep` and `awk` (the portable subset itself).

**Covered** (what a Mac runs: dotfiles' install and sync, bare `cpd`, a Worker or Lead on a Mac, the Gate there): `scripts/install-cpd.sh`, `scripts/pi-check.sh`, `scripts/pi-check-pty.py` (its pty runner), `scripts/check-portable.sh` (itself), `scripts/check-migrations-frozen.sh`, `scripts/cargo.sh`, `scripts/pnpm-fresh.sh`, `scripts/new-migration.sh`, `scripts/preview-tui.sh`, `scripts/repin.sh` (a Lead resolving a schema-pin conflict, on any machine), `scripts/sync-version.sh`, `scripts/tag-version.sh`. **Linux-only, not covered**, each with its reason in the check's own list: `scripts/prune-worktrees.sh` (a one-time cleanup run on hs; now only `exec cpd prune`, see docs/commands.md §26), `scripts/test-time.sh` (measures the Gate's run on hs: `date +%s.%N`, `uptime`). **A script of `scripts/` in neither list fails the check** (`<file>: not classified: add it to the covered or the Linux-only list`), so a new script cannot skip the decision. The two lists are data at the top of the script.

**Refused patterns**, applied to every line that is not a full-line comment (first non-blank character `#`, so a header may name what it avoids). The output names the alternative:

| Pattern | Alternative |
|---|---|
| `renameat2`, `RENAME_EXCHANGE` | `os.replace` (`rename(2)`) of a symlink over the path ("The adapter swap") |
| `/proc/`, `/sys/` | `uname`, `ps -o <field>= -p <pid>`; for a UUID `node -p 'crypto.randomUUID()'` |
| `readlink -f`, `-e`, `-m`; `realpath` | `cd "$dir" && pwd -P`; `python3 -c 'import os,sys; print(os.path.realpath(sys.argv[1]))'`. Plain `readlink <link>` is allowed |
| `stat -c`, `stat --` | `python3 -c 'import os,sys; print(os.stat(sys.argv[1]).st_mtime)'`, or `[ a -nt b ]` |
| `date -d`, `date --date`, `%N` in a `date` format, `date -r <seconds>` | `date -u +<format>` of now; parse and compute dates in `python3` |
| `sed -i` not directly followed by a suffix (`-i.bak` is allowed), `sed --in-place`, `sed -r` | write to a temporary file and `mv` it; `sed -E` |
| `flock` | `python3 -c 'import fcntl,sys; fcntl.flock(open(sys.argv[1], "a"), fcntl.LOCK_EX \| fcntl.LOCK_NB)'` (exit 1 when held): the same `flock(2)` lock cpd takes (`core/src/lock.rs`); macOS ships no `flock` command |
| `timeout` (the command), `setsid` | a background process and `kill`; `python3` `subprocess` with `timeout=`; neither ships on macOS |
| `xargs -r`, `xargs --no-run-if-empty`, `xargs -d` | `while read`; a `[ -n "$list" ]` guard |
| `grep -P`, `grep --perl-regexp` | `grep -E`, `sed -n`, or `awk` |
| `sha256sum`, `sha1sum`, `md5sum` | `shasum -a 256`, `shasum -a 1` (on both) |
| `nproc` | `getconf _NPROCESSORS_ONLN` |
| `mv -T`, `ln -T`, `cp --reflink`, `cp --parents`, `find -printf`, `mktemp --…`, `touch -d`, `base64 -w`, `sort -V`, `du -b`, `df --output` | the POSIX form of the same, or `python3` |

The table is `pattern|alternative` data in the script: a new Linux-only habit is one line there and one test. **Exemption:** a line that ends in `# portable: <reason>` (a non-empty reason; the check counts and prints the number) is not checked. It is for a line the patterns misread (a message that quotes a pattern) or one that a `uname` guard already routes around, with the reason written there; never for a call that would run on a Mac. A `# portable:` with no reason is itself a hit.

## The scoped loop

The full suite is the Gate's (hs-d338): while you edit, run only the tests your change can reach. Measured on hs (docs/research/build-cycle.md §5), an edit and its scoped tests take 3.7-12 s, almost all of it rustc; the tests themselves take 0.01-0.04 s. With one binary per area, a module edit's scoped run (`scripts/test-changed`, build included) took 1.6-2.2 s on hs (Plan quality, lp-areas), against 10-11 s when all integration tests were one binary.

- **`scripts/test-changed [--dry-run] [<base>]`** runs the tests that the changed files can reach, with `scripts/cargo.sh nextest run`. `<base>` is a git revision, `origin/main` by default; the changed files are those that differ between `<base>` (its merge base with `HEAD`) and the working tree: committed, staged, unstaged and untracked files. The selection:
  1. A changed file belongs to the crate whose directory holds it (`cargo metadata`: `core/` is `cpd-core`, `engine/` is `cpd-engine`, `tui/` is `cpd-tui`, `cli/` is `cpd`). The run is those crates **and their reverse dependencies** (`-p <crate>` for each): a change in `core/` runs `cpd-core`, `cpd-engine`, `cpd-tui` and `cpd`; a change in `engine/` runs `cpd-engine` and `cpd`; a change in `tui/` runs `cpd-tui` and `cpd`; a change in `cli/` runs `cpd`.
  2. **Integration tests are selected by area binary** (one binary per area, `cli/tests/<area>/main.rs`, see Tests; a test's name is `<module>::<test>`): a changed `cli/tests/<area>/<module>.rs` selects that module in its binary only, `-p cpd --test <area> -E 'test(/^<module>::/)'`; a changed `cli/tests/<area>/main.rs`, or any other file of that area's directory that is no module, selects that binary: `-p cpd --test <area>`. `--test` makes cargo build and link only the named binaries. Changes in several areas run the union, each with its own filter (`-E 'binary(<area>) & test(/^<module>::/)'`, or `-E 'binary(<area>)'` for a whole binary). A directory of `cli/tests/` that holds no `main.rs` (`common/`) is shared by every binary, so it selects the whole crate `cpd`, as in 1, and so does a change in `cli/src/` beside it.
  3. When several rules select tests, the run is their union.
  4. **The full suite** (`nextest run --workspace`) is the fallback when a changed file is a root-level input that no crate's selection can bound: the root `Cargo.toml`, `Cargo.lock`, `rust-toolchain*`, any `build.rs`, anything under `.config/`, anything under `core/src/store/migrations/`, and `scripts/cargo.sh`. It wins over 1-3.
  5. A changed file outside every crate and not in 4 (`docs/`, `pi/`, other scripts) selects no Rust test. With nothing selected, `test-changed` says `test-changed: nothing to run` on stderr, runs nothing and exits 0.
- **`cpd test changed [--dry-run] [<base>]`** (commands.md §26.1) is the logic of this loop; `scripts/test-changed` is `exec cpd test changed "$@"`, with the same arguments and output. `cpd test run <name>...` (§26.2) is the logic of `scripts/tests.sh run`; `scripts/tests.sh build | list | run` keeps its argument contract for `.config/cpd.toml` `[tests]`, and its shell stays until `cpd test` passes its tests. Both are tested in-process on `Fakes` (`Runner` routes with canned `git diff` and `cargo metadata` output); the scripts that must exist before cpd does (`cargo.sh`, `pnpm-fresh.sh`, `preview-tui.sh`, `check-portable.sh`, `test-time.sh`, `pi-check.sh`, `tripwire/`) keep their own exec tests as the named exception.
- **`--dry-run`** prints the one command it would run (for example `scripts/cargo.sh nextest run -p cpd-core -p cpd-engine -p cpd-tui -p cpd`) on stdout, and nothing else, and does not run it; it exits 0. Use it to see what a change reaches.
- Otherwise it runs that command and exits with nextest's status. Inside its selection it runs every test: it never skips, filters or weakens one (the selection is by files; the Gate runs everything).
- A Worker session refuses an unfiltered full run (hs-d338), so where the fallback in 4 applies there, `scripts/test-changed --dry-run` shows the full command and you run the tests you changed by name (`-p cpd --test <area> -E 'test(/^<module>::/)'`, see Running cargo).
- **bacon** (a developer's tool, not a dependency; the Gate does not use it) watches the checkout and reruns on save. `bacon.toml` at the root has two jobs: `fast`, the default (`bacon`), runs `scripts/test-changed`; `full` (`bacon full`) runs the whole suite, `scripts/cargo.sh nextest run --workspace`. Both go through `scripts/cargo.sh`, so sccache and the `$CARGO` lookup apply.

## Debuginfo

The `dev` profile builds with `debug = 0` (no debuginfo), and `test` inherits it, so cargo builds, nextest and the Gate all use it. Why: debuginfo costs build time and `target/` space (tests-build-F2: full debuginfo 48-62 s and 4.7G, line tables 33-40 s and 2.4G, for a clean test build), and the tests never read it. The measurement for `debug = 0` is in the commit that sets it (Plan quality, dl-config), and `Cargo.toml` keeps the reason beside the setting.

- **What a failure shows.** A panic still prints its message and `file:line:col` (the panic location is compiled in, it is not debuginfo). A backtrace (`RUST_BACKTRACE=1`) lists the function names, from the symbol table, with no `at file:line` under a frame; neither do the frames of dependencies and `std`.
- **Line tables back for a debugging session**, with no edit to `Cargo.toml`: set `CARGO_PROFILE_DEV_DEBUG=line-tables-only`, for example `CARGO_PROFILE_DEV_DEBUG=line-tables-only RUST_BACKTRACE=1 scripts/cargo.sh nextest run -p cpd-core -E 'test(/^<module>::/)'` (it applies to `test` too). `CARGO_PROFILE_DEV_DEBUG=true` gives full debuginfo, for a debugger. A different setting is a different build: cargo rebuilds the crates when you switch it on and again when you unset it, so use a `CARGO_TARGET_DIR` of its own for a long session.

## The version string

`cpd --version`'s `version` is `<semantic version>-<commit>` (commands.md §1.2), where the semantic version `0.<protocol>.<migrations>` is derived from `PROTOCOL` in `core/src/events/kind.rs` and the count of `.sql` files in `core/src/store/migrations/` (docs/versioning.md). The Cargo.toml version is derived and checked: a test fails when it differs (contract §4.5; `scripts/sync-version.sh`, a thin `exec cpd version sync [--print]`, rewrites it from kind.rs and the directory; commands.md §26.2).

- **The commit comes from the environment, not from git.** `cli/build.rs` reads `CPD_COMMIT` (a short hash such as `070ddee`) and declares `cargo:rerun-if-env-changed=CPD_COMMIT`; it runs no `git` command and watches no `.git` file. So a commit in a worktree rebuilds nothing (the build script used to watch `HEAD` and the branch ref, which rebuilt `cpd` on every commit, 4 s: docs/research/build-cycle.md §7), and a build whose `CPD_COMMIT` changes rebuilds `cpd` and reports the new hash.
- **Who sets it:** `scripts/install-cpd.sh` (the installed binary, which `cpd install` then installs) and the Gate (`pnpm run verify`), each to `git rev-parse --short HEAD` of the checkout it builds. An installed or released binary therefore reports exactly the commit it was built from.
- **The fallback**, when `CPD_COMMIT` is unset or empty (a plain `cargo build` or test run in a worktree): `<semantic version>-dev`, for example `0.13.45-dev`. It names no commit: a build never claims a commit it was not given. `-unknown` is no longer produced. No dirty marker is added and git tags are not read.
- `CPD_VERSION` (the value `cli/src/cli.rs` reads with `env!`) is set by `build.rs` alone.

## Checking a pi version

`scripts/pi-check.sh [<pi command>]` (default `pi`) checks that the adapter `pi/` of the checkout it lives in loads and activates in that pi, offline: an empty temporary `PI_CODING_AGENT_DIR` and `HOME`, `PI_OFFLINE=1`, no credentials and no network route (below), nothing written outside a temporary directory (removed on exit). It runs:

0. **Tools** (hs-d355): `python3` and `node` are on `PATH`, else `pi-check: FAIL: step 0 (tools): <tool> is not installed (step 3 needs it)` and exit 1. Never a skip and never an `ok`: a machine that cannot run the check fails it.
1. **Version:** `<pi command> --version` succeeds; its output is printed.
2. **Load:** `pi --no-extensions --no-session -e pi/ --mode rpc </dev/null` with no `CPD_*` variables must exit 0 (an extension that throws at load exits 1).
   `pi-check` starts pi with `--no-extensions -e <adapter>`, which has no built-in MCP either, so it exercises the adapter's mount (contract §6.11) alone, as production does with `--no-mcp`. The mount depends on pi's exported `createMcpExtension`, so a pi bump re-runs it.
3. **Activation:** the adapter only activates in interactive mode, which pi enters only when stdin and stdout are ttys, so pi runs on a pty made by `scripts/pi-check-pty.py` (python3's `os.openpty`, no multiplexer; the Context decision to leave tmux is pro-d14), with `CPD_SESSION` equal to pi's session id (`--session-id`), `CPD_HOME` set, and a fake `cpd` first on `PATH`. It passes when the fake was called with `events follow`. The runner: sets the pty to 120x30 (`TIOCSWINSZ`) before pi starts; starts pi as a session leader with the pty as its controlling terminal (`start_new_session`, `TIOCSCTTY`); drains the pty in the same `select` that waits for the pass (a write by the fake `cpd` to a fifo, `$tmp/follow`) and for pi's end (`SIGCHLD` on a wake-up descriptor: no `waitpid` poll and no `sleep` loop); fails (exit 1, the reason on the first line of its `--out` file, the last 4000 bytes pi drew after it, which `pi-check.sh` shows with pi's stderr and the fake's calls) when pi ends first (`pi exited with status <n>`) or when `PI_CHECK_ACTIVATION_SECS` (default 60) pass first; and on every path, and on `SIGTERM` and `SIGINT` (exit 130), kills pi's whole process group with `SIGKILL` and waits until no member is left before it returns. pi needs no terminal capability reply on a bare pty: the pinned pi starts without one (verified: the real pinned pi 1.3.0 passes this check on a bare pty). The fake `cpd` blocks for `events follow` on a second fifo nobody writes (`$tmp/hold`), not on `sleep`; the runner kills it with pi's group. Everything stays inside `$tmp` (the fifos, the fake, pi's `HOME` and `TMPDIR`), removed with it.

Exit 0 with `pi-check: ok (<version>)`; exit 1 with `pi-check: FAIL: <step and why>` and the tail of pi's output. It does not run `pnpm test`.

**The cleanup cannot fail a pass** (hs-d463; incident: on macOS pi-check printed `pi-check: ok (1.3.0)`, then its cleanup, `rm -rf "$tmp"`, failed `Directory not empty` because a child of pi's pane was still writing into `$tmp`; under `set -e` the trap's failure became the script's exit status, so the check exited non-zero and dotfiles did not move the pi pin). The rules:
- **The exit status is the check's, fixed before the cleanup runs.** The `EXIT` trap saves `$?`, runs with `set +e`, every command in it guarded (`|| true`), and ends with an explicit `exit <saved status>`: a pass stays 0, a `FAIL` stays 1, a signal stays 130. Nothing the cleanup does can change it. The `pi-check: ok (<version>)` line and each `FAIL` line are printed by the check, never by the cleanup.
- **It stops and waits for its children first.** In order: (1) if the runner still runs (a signal reached the script), `SIGTERM` it and wait for it: the runner kills pi's process group with `SIGKILL` and waits until the group has no member before it returns (at most 400 polls of 5 ms of a `select`, never a `sleep`); (2) `rm -rf "$tmp"`, and if it fails (a child still writing, `Directory not empty`, `Resource busy`), **retry it every `PI_CHECK_CLEANUP_PAUSE` seconds (default 0.5, `python3 scripts/pi-check-pty.py pause`, a `select` with no descriptor) for at most `PI_CHECK_CLEANUP_SECS` (default 5) seconds' worth of tries**, the same environment override as `CPD_INSTALL_LOCK_WAIT_SECS`, for the tests (they set the pause to 0 so no test waits). Every wait is bounded; none loops forever.
- **A cleanup that still fails warns and does not fail.** After the last retry it prints one line `pi-check: warning: could not remove <tmp>: <rm's message>` on stderr, and the exit status is still the check's. It never prints `pi-check: FAIL` for a cleanup.
- **The tests** (`pi/test/pi-check.test.ts`: run `scripts/pi-check.sh` with a fake `<pi command>`, a node script of the test that writes what it saw to files, and a fake `rm` first on `PATH`; no real pi, no tmux, no `sleep`, no wall-clock bound): (a) the fake `rm` fails the first two calls with `rm: <tmp>: Directory not empty` and then really removes: exit 0, the `ok` line, `$tmp` gone; (b) the fake `rm` always fails, `PI_CHECK_CLEANUP_SECS=1`: exit 0, the `ok` line, the warning line; (c) the same fake `rm`, and the check **fails** (a pi that exits non-zero at step 1): exit 1, the `FAIL` line, the warning, never exit 0; (d) the fake pi records its pid, its tty (stdin and stdout are ttys of 120x30) and the pid of a child of its own that never ends: when the check passes, both are dead; (e) the fake pi sends `SIGTERM` to its parent, the runner, then hangs: exit 130, `$tmp` removed, both pids dead; (f) a pi that exits 3 before it follows: `FAIL: step 3 (activation)` with `pi exited with status 3`, no child left; (g) a pi that never follows with `PI_CHECK_ACTIVATION_SECS=0`: `FAIL: step 3 (activation)` at once; (h) a `PATH` without `python3`, and one without `node`, fails step 0; (i) the negative half of the old real-pi test: the fake pi parses the fake's `session show` answer with the adapter's own `parseSession`, and the check fails at step 3 when the adapter requires a field `answers.ts` lacks (the Gate step runs the real pinned pi, so `pnpm test` does not run it a second time).

**The fake cpd has one source of truth with the adapter's tests** (hs-d355; incident: the fake answered `session show` with four fields, the adapter had come to require `role` and `context` too, rejected the answer as `bad_output`, never ran `events follow`, and step 3 failed for every pi version; its `policy show` and `--version` answers, `{"ok":true}`, are rejected by the adapter too). The answers the adapter parses at activation live in `pi/test/answers.ts`, which exports `answers()`: a map from the key of `Fixture.respond` (`pi/test/fake.ts`: `session-show`, `context-pending`, `policy-show`, `--version`) to the answer, built with `sessionShow()`, `policyShow()` and `PROTOCOL` from `pi/lib/event.ts`, so not even the protocol number is a hand-kept copy. Two users, and nobody else holds an answer:
- the `Fixture` constructor of `pi/test/fake.ts` takes its four default `respond` calls from `answers()`; `sessionShow` and `policyShow` move to `answers.ts` and `fake.ts` re-exports them, so no test changes;
- `node pi/test/answers.ts <cpd argv…>` (Node's native type stripping, as the tests run) prints the entry for the key of the argv (`<a>-<b>`, `--version`) as JSON and exits 0; with no entry it prints `{"ok":true}`, as the tests' fake does. pi-check's fake `cpd` is a `sh` script that records its argv, writes to the `follow` fifo and blocks on the `hold` fifo for `events follow` (no `sleep`), and otherwise `exec node "$root/pi/test/answers.ts" "$@"`. It holds no JSON of its own.

So a field, a command or a protocol number the adapter starts requiring is added once, in `answers.ts` (the real shape is `commands.md`'s). Until it is, `pnpm test` fails (every test that starts the adapter, and a new `answers.test.ts` that parses each answer with the adapter's own parsers: `parseSession`, `policySection`, the protocol check) and, in the same Gate run, pi-check's step 3 fails, because the adapter rejects the answer and never follows.

**The fake cpd refuses what cpd refuses** (pro-d311; incident pro-d307: `pi/lib/turns.ts` called `plan show <plan>` for hours in every Context, a call cpd refuses, because the Fixture answered by the first two words of the argv, so every test passed). `FakeCpd.call` of `pi/test/fake.ts` first asks `usageError(argv)` of `pi/test/usage.ts`. A message is answered as cpd answers, exit 2 and `{"ok":false,"error":{"code":"usage","message":<it>,"details":{}}}`, before any `respond`ed answer, and the call still shows in `Fixture.argvs()`. So a test that wants an argv to succeed passes an argv cpd accepts. The grammar it checks is `pi/test/cpd-usage.json`: one JSON object, keys sorted, two-space indent, one trailing newline.
- **A key** is a runnable command path as space-joined words (`plan show`); the root `cpd` is the key `""`. Every runnable command is a key, hidden and internal ones too; `help` is not a command.
- **A value** is `{"flags": {"--plan": true, "--help": false}, "positionals": {"min": 0, "max": 0}, "required": []}`. `flags` holds every long flag the command accepts: its own, the global ones it inherits, and clap's `--help` (`--version` for the root only); `true` when the flag takes one value, `false` when it takes none. Short flags are not recorded. `positionals.min` is the number of required positional arguments and `max` the number of positional arguments, `null` when it takes any number. `required` lists the long flags clap requires unconditionally (`required(true)`, not an ArgGroup member).
- **The generator and the pin.** The file is derived, never edited by hand. The Rust test `usage_grammar::usage_file_is_generated_from_the_binary` of `cli/tests/tooling/usage_grammar.rs` builds the same tree as `cpd --help`, fails when the file and the binary differ, and rewrites the file under `CPD_BLESS=1 scripts/cargo.sh test -p cpd --test tooling usage_grammar`. The generator fails loud (panics, naming the command and the argument) on a flag that takes other than 0 or exactly 1 value, because the file cannot express it.
- **The validator** `pi/test/usage.ts` exports `export type CommandUsage = { flags: Record<string, boolean>; positionals: { min: number; max: number | null }; required: string[] }`, `export type Grammar = Record<string, CommandUsage>`, `export const grammar: Grammar` (the shipped file) and `export function usageError(argv: string[], g: Grammar = grammar): string | undefined`. `argv` is what the adapter passes to `call`, without the leading `cpd`. It returns `undefined` when cpd would accept the argv, and otherwise a clap-style message naming the offending token or flag in single quotes (`unexpected argument 'p1' found`, `unrecognized subcommand 'frob'`, `a value is required for '--plan' but none was supplied`, `the following required arguments were not provided: --title`). A test asserts only the quoted token, never the whole sentence. Its procedure:
  1. The command path is the longest run of leading words, up to the first token that starts with `-`, that is a key; the root `""` when there is none and the first token starts with `-` or argv is empty. A leading word that continues no known path is `unrecognized subcommand`. A path that stops at a group (a prefix of keys that is not a key, such as `plan`) with no further word is refused with a message that names it (`a command is required after 'plan'`). Argv with no token at all is not judged.
  2. Then each remaining token in order: a bare `--` makes every later token positional; `--name` or `--name=value` must be a key of `flags` (else `unexpected argument`); a flag that takes a value and has no `=value` consumes the next token, whatever it starts with (none left: `a value is required`); a flag that takes none and has `=value` is refused; a token with a single dash is never judged; any other token is a positional.
  3. At the end the positional count must be within `min` and `max` (an extra one: `unexpected argument '<it>' found`), and every flag of `required` must be present.

  It is sound, not complete: it never refuses an argv clap accepts. It does not model conflicts, ArgGroups or the validity of a value. Not covered: those, the follower's `spawn` argvs, the durable-worker fakes, and pi-check's fake (`pi/test/answers.ts`, `scripts/pi-check.sh`).

**pi-check never starts a model turn** (hs-d355; incident: the adapter posts its error as a message, which starts a turn; on hs it reached gemini and got a 429, though the check claims to be offline with no credentials). Two things, both required: the fake answers what the adapter parses (above), so it posts no error; and pi has nothing to call a model with, whatever the caller's environment holds. **Every pi command (steps 1 to 3, the pty's command) runs under `env -i` with an allow-list**: `PATH`, `LANG`, `LC_ALL`, `LC_CTYPE` and `TERM` when the caller has them, plus what pi-check sets itself: `HOME` (`$tmp/home`), `TMPDIR` (`$tmp`), `PI_CODING_AGENT_DIR` (`$tmp/agent`), `PI_OFFLINE=1`, `PI_SKIP_VERSION_CHECK=1`, and for step 3 `CPD_SESSION` and `CPD_HOME`. Nothing else crosses: no provider key (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY`, `GOOGLE_API_KEY`, …), no cloud credential (`AWS_*`, `GOOGLE_APPLICATION_CREDENTIALS`), no proxy or route (`HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY` and their lower-case forms), no `*_BASE_URL`. The temporary `HOME` and agent directory hold no `auth.json`, settings or models file. The test gives pi-check, as `<pi command>`, a script that writes its environment to a file and exits 0, run with those variables (and `FOO_API_KEY`, `SOME_BASE_URL`) set in the caller's environment: every recorded name must be in the allow-list or set by pi-check, apart from `PWD`, `SHLVL` and `_`, which a shell adds.

**In the Gate** (hs-d355): `pnpm run verify` runs `scripts/pi-check.sh node_modules/.bin/pi` after `pnpm test` and before the cargo steps. That pi is the one `package.json` pins (`@earendil-works/pi-coding-agent`, an exact version, installed by `pnpm install --frozen-lockfile`, which `preverify`'s `scripts/pnpm-fresh.sh` runs when `node_modules` is stale), so the Gate checks the current adapter against the pinned pi, with no `pi` on `PATH` and no dotfiles. A missing `node_modules/.bin/pi` fails step 1 (`pi-check: FAIL: step 1 (version): 'node_modules/.bin/pi --version' failed`); a missing `python3` or `node` fails step 0. The Gate does not skip on a machine that lacks them: the failure is the signal. A fake that falls behind the adapter therefore fails the Gate on hs, not a Mac's `bootstrap.sh`.

dotfiles runs it (hs-d145) after updating the `cpd` checkout and before activating a new pinned pi on a machine: `scripts/pi-check.sh <path of the new pi>`; a failure leaves the active pi as it was. It runs on a Mac too, which is why "The portability check" covers it.

## Measuring tool-result bloat (hs-d737)

**Command.** `node pi/measure/session-bloat.ts [--root <dir>] [--since <ISO time>] [--until <ISO time>] [--top <n>] [--json]`; it reads every `*.jsonl` file one directory below `--root` (default: pi's agent sessions directory, `~/.pi/agent/sessions`), never writes or changes a file, and exits 0 with a report. A bad option, a bad time or an unreadable root exits 2 with one line on stderr (no silent default).

**Window.** A session is in the window when its header `timestamp` is >= `--since` and < `--until` (both optional).

**Role** of a session, from the last `session_info` `name` in its file (a heuristic): a name of two words and `a<digits>` (`<plan> <job> a<n>`) is `worker`; a name ending `-manager` is `manager`; any other name is `lead`; no name is `other`.

**Per role** it reports:
- `sessions`: the number of sessions.
- `turns`: the number of assistant messages.
- `tool_results`: the number of toolResult messages.
- `result_chars`: the sum of the text blocks of every toolResult; images count 0.
- `result_tokens_est`: ceil(result_chars / 4), pi's own estimate (pi docs/settings.md `codemode.inlineBudget`, not the provider's count).
- `usage`: `{input, output, cache_read, cache_write, cost_usd}` summed over the assistant messages.
- `by_tool`: `[{tool, calls, chars}]` sorted by chars, largest first, cut to `--top` (default 10).
- `top_commands`: `[{key, calls, chars}]` the same way, where the key of a `bash` result is the first two whitespace-separated words of the `command` of the toolCall with the same id (`bash ?` when no call has that id) and the key of any other result is its tool name.
- `largest`: the `--top` single results `[{chars, tool, command, file, entry}]` (command = the first 80 characters of the call's `command`, or empty; file = the file's base name; entry = the message entry's `id`).
- `codemode`: `{calls, output_chars, nested: [{name, calls}]}` (the `codemode` toolResults, their output size, and the calls they made by tool name from `nestedCalls.calls[].name`, sorted by calls).

**Report.** With `--json` one JSON object `{window: {since, until}, files, skipped_lines, roles: {worker, manager, lead, other}}` where each role holds the fields above (a role with no session is present with zeros and empty lists), `since` and `until` null when not given; without `--json` the same numbers as plain text, one line per row. `skipped_lines` counts the lines that are not JSON in all files (a live session's last line may be cut): they are skipped and the count is in the report, never hidden.

**What it cannot measure.** What a codemode script read and filtered away (nested results are never stored), so the saving shows only as a change in `result_chars`, `turns` and `cost_usd` between two windows of comparable work; sessions differ, so compare medians over many sessions, not one pair.

**How to use it for the experiment.** The baseline is `--until <time the project setting reached the machine>`, the comparison `--since` that time.
