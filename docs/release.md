# Releases and versioning

cpd is in alpha. Versions are 0.0.x; the first tagged release is 0.0.5.

## Version string

The displayed version in `cpd --version` and the StatusBar's right end shows `<Cargo.toml version>-<short commit hash>`, for example `0.0.5-070ddee`. The hash is the output of `git rev-parse --short HEAD`. If git is unavailable or fails, the version is `<version>-unknown`. No dirty marker is shown. Git tags are not read.

A build between releases (on main, in a worktree, a preview binary) shows the last release's version with its own commit hash, so it is identifiable.

## Release procedure

Releases are manual. The User decides the next milestone and tells the Manager, who or a Lead runs the release on `hs`.

### Step 1: Cut the release (on hs)

```bash
scripts/release.sh 0.0.5
```

This command:
- Creates a temporary worktree on branch `release/v0.0.5` from `origin/main`
- Bumps `Cargo.toml` and `Cargo.lock` using cargo-release
- Writes `CHANGELOG.md` using git-cliff
- Runs `npm run verify` (the Gate, executed first)
- Pushes and opens a PR titled 'Release 0.0.5' with `gh`

The User merges the PR on GitHub (squash merge).

### Step 2: Tag the release (on hs)

After merge:

```bash
scripts/release.sh tag 0.0.5
```

This command tags the squash commit `v0.0.5` (annotated) and pushes the tag.

## CHANGELOG

`CHANGELOG.md` at the repo root is generated by git-cliff from squash-commit subjects (the PR title plus ` (#n)`) since the previous `v*` tag.

Format: a flat list per release under `## [<version>] - <YYYY-MM-DD>`. The Release commit itself is excluded.

The first release's section (0.0.5, when no `v*` tag exists) is: "First tagged release: the Rust cpd, event protocol 4. Earlier history: git log."

## Tools

cargo-release and git-cliff are pinned in `~/dotfiles` and installed on `hs` only. Config files at the repo root: `release.toml` and `cliff.toml`.
