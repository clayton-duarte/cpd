# `gh` CLI or GitHub GraphQL API for the 5-s PR poll

Job `research-gh` of Plan `pr-poller` (Context records hs-d65, hs-d72, hs-d96, hs-d97; assumptions A1, A2, A6, A10). The poll is one GraphQL `search` of the User's open PRs every 5 s. Two ways to send it: the `gh` CLI as a subprocess (as `core/src/pr/gh.rs` does today), or an HTTPS POST to `https://api.github.com/graphql` from the Rust binary. This file measures both and recommends; it changes no code. The User decides.

## Method and evidence

- Run 2026-10-16 (18:30–19:10 UTC) on the User's machine, against the User's real account `clayton-duarte`, at commit `044ce97`. Only GraphQL queries and REST GETs (`rate_limit`); no mutation. The rate limit was never approached (about 350 of 5,000 points used in the window by all of this research, including 37 heavy public-repo scans).
- `gh` 2.45.0 (`gh --version`); Rust 1.99.0; `ureq` 3.4.2 (rustls + ring); 16 cores (`nproc`), load about 3.7 (`uptime`), so numbers are for a quiet-ish machine.
- Scratch project outside the repo (`/tmp/cpd-gh-research/`, deleted at the end): `probe` (a `ureq` client with the modes `persist N SLEEP`, `oneshot`, `once`) and `base` (the same program through a `gh` subprocess). The poll query is the Job's, verbatim (file `poll.graphql`). The account has 3 open PRs, so every response is small (about 3 KB); the cost and latency of a 100-PR page were not measured (**unverified**).
- "CLI" = `gh api graphql -F query=@poll.graphql`. **`-f query=@file` as the Job wrote it does not work in gh 2.45.0**: `-f` sends the literal text `@poll.graphql` (error `Expected one of SCHEMA, SCALAR, … actual: DIR_SIGN ("@")`). `-F` reads the file.
- Everything not run is marked **unverified**.

What the table says: the call is **dominated by GitHub, not by the interface**. The trivial query costs 0.2–0.3 s, the poll 1.4 s, and the search alone (the poll without `commits`) 1.17 s median (n = 20, `probe persist 20 1`); `statusCheckRollup` directly on the PR (see item 6) 1.36 s; the whole poll 1.41 s. The difference between the options is about 0.1 s of latency, **70 ms of CPU and 29 MB of RSS per poll**, against 2.9 MB of binary, 14 s of build and 22 new crates.

Two consequences for the engine, whichever option: a poll can take longer than 5 s (max 5.7 s in 35 calls; GitHub's own timeout is 10 s), so the next poll must start 5 s after the previous one **ended** (or be skipped), never overlap; and the 60 s `TIMEOUT` of `gh.rs` is too long for a 5-s loop (see failure 2).

## Rate cost

Source: `gh api graphql … rateLimit { cost remaining resetAt }`, the `x-ratelimit-*` headers of `gh api -i`, and the GraphQL docs <https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api> (fetched today).

| Query | `rateLimit.cost` (measured) | Note |
|---|---|---|
| The poll query (A1), `first: 100`, 3 PRs in the account | **1** (repeated: 4 times, always 1) | docs formula: 1 search + 100 `commits` connections = 101 requests, /100, minimum 1 |
| The A6 lookup, 3 aliased `repository(...) { pullRequest(number:) { state mergedAt } }` | **1** | returned `MERGED` + `mergedAt`, `MERGED`, `CLOSED` + `mergedAt: null` |
| Proof the cost follows the `first:`/`last:` limits, not the result size | poll + `comments(first:100)` = **2**; + `reviews(first:100)` = **3**; search only = **1** | 100 results never needed: the cost of the real query is 1 even when there are 3 PRs; adding a nested connection of 100 per PR adds 1 each |
| A query that fails (syntax error, unknown field) | **still counted**: `x-ratelimit-used` rose by 1 per failed call (267 → 270 over four calls) | the 401 (bad token) calls carry no rate headers |

- **Hourly budget at 5 s:** 3,600 / 5 = **720 polls = 720 points** an hour, 14.4 % of the 5,000-point primary limit (`x-ratelimit-limit: 5000`, `x-ratelimit-resource: graphql`; docs: "5,000 points per hour per user"). Every other `gh` use of the User (`gh pr view` is GraphQL too) shares the same 5,000: `x-ratelimit-used` was already 143 at my first call. A6 lookups add 1 point each, only when a PR leaves the search. More than 100 open PRs need a second page (cost 1 more; `issueCount` tells; **unverified** with 100+ PRs).
- A10 (`remaining < 100` → pause until `resetAt`): both exist in every response (`rateLimit.remaining`/`resetAt`, headers `x-ratelimit-remaining`/`-reset`). **Caveat measured:** `remaining` is not an exact running count. Two consecutive calls once returned the same `remaining` (4729), and `GET /rate_limit` (REST) showed `graphql` `used: 30` and a reset at 19:16 while the GraphQL `rateLimit` object said `used: 271`, reset 19:50:30, in the same minute. Read the numbers from the poll's own response; do not call `/rate_limit`. A 100-point margin out of 5,000 is large against that skew.
- **No separate search limit for GraphQL `search`:** its responses say `x-ratelimit-resource: graphql`; `GET /rate_limit` `resources.search` (REST: 30 a minute, docs <https://docs.github.com/en/rest/search/search>) stayed `used: 0` around a poll. The 30/min and the 10/min code-search limits are REST-only.
- **Secondary limits** (docs, same page): at most 100 concurrent requests; 2,000 points a minute on the GraphQL endpoint (a poll is 1 point; 12 a minute); "no more than 90 seconds of CPU time per 60 seconds of real time … no more than 60 seconds of this CPU time may be for the GraphQL API. You can roughly estimate the CPU time by measuring the total response time". At 1.4 s per call and 12 calls a minute that is about **17 s of every 60, about 28 % of the 60 s GraphQL allowance**, whatever else the User runs at the same time. This is the number to watch, not the points (docs-based; how GitHub meters it is **unverified**).
- **What the docs say about polling** (<https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api>, GraphQL page "Staying under the rate limit"): "subscribe to webhooks instead of polling"; if polling, "poll only as often as you need to, on a fixed schedule", honour `x-poll-interval` (REST). No minimum interval is stated for reads. Conditional requests (`ETag`, `304` free of charge) are a REST feature: **a GraphQL POST has no `ETag` response header** (`gh api -i graphql`), so no free 304.
- Primary limit exceeded: docs say status **200** with an error message and `x-ratelimit-remaining: 0`; secondary limit: status **200 or 403** with an error message naming a secondary rate limit, `retry-after` when present (else wait at least 1 minute, then back off exponentially). Not provoked (out of scope).

## Auth and operations

| Question | CLI | Direct API |
|---|---|---|
| Where the token comes from | `gh` itself: `GH_TOKEN`, else `GH_ENTERPRISE_TOKEN`, else `~/.config/gh/hosts.yml` (this machine: plaintext, mode 600, no keyring) | `gh auth token` (0.03 s, stdout = the token; `--hostname`, `--user` exist). **It honours the same order**: here `gh auth token` printed exactly `$GH_TOKEN`, not the `hosts.yml` token (the two differ). So both options use the same credential |
| User runs `gh auth login` again, or the token is revoked/expires | the next `gh` call reads the new file: nothing to do. `gh` OAuth tokens (`gho_…`) have no expiry by default (**unverified**) | a cached token goes stale: 401 → run `gh auth token` again once and retry once (as the Job says). **If `GH_TOKEN` is in cpd's environment (it is for this Worker), the re-read returns the same dead token** until `cpd watch` is restarted with a new environment; the CLI has the same problem since it inherits the same environment |
| Several accounts / `gh auth switch` | `gh` uses the active account; `author:@me` is that account's | `gh auth token` returns the active account's token; same. `gh auth status` here lists the same account twice (once for `GH_TOKEN`, once for `hosts.yml`, "Active account" true only for the first). **Either way, after a switch every PR of the old account leaves the open search, and A6's lookup answers `OPEN`**: the poll must treat "state OPEN but not in the search" as unknown, not as closed or merged |
| Several hosts (GitHub Enterprise) | `gh` picks the host from `GH_HOST` or the repo's remote | the URL (`https://<host>/api/graphql`) and `gh auth token --hostname <host>` must be chosen by cpd; the poll as designed is for one host (**not measured**; no GHE here) |
| A secret in cpd's process or logs | the token never enters cpd's memory (only `gh`'s, for 1.4 s); never in `argv`; `gh_failed` `details.argv` is the query file path, not a secret | the token lives in the engine's memory for its whole life; `ureq` errors printed (`Io`, `Timeout`) carry no header; **no request, header or `Debug` of an agent may reach an Event, a log or `details`** (a rule to enforce with a test) |
| Proxy / corporate CA | `gh` handles `HTTPS_PROXY`, `SSL_CERT_FILE` | `ureq` handles `HTTPS_PROXY` (tested); it trusts `webpki-roots` (bundled Mozilla roots), **not the system store**, so a TLS-intercepting proxy with a private CA fails (**unverified**: needs `rustls-native-certs`, one more crate) |
| `gh` version | 2.45.0 here (the `-f`/`-F` trap above); `gh pr view/create` already require it | none, but `gh` stays a system dependency (hs-d3) for `pr view`, `pr create` and `auth token` |

## Recommendation

- **Poll through the Direct API (`ureq` + rustls); keep `gh` for `pr view`, `pr create`, `auth token` and the A6 lookup if the User prefers fewer paths.** The poll is the only call that runs 720 times an hour: the CLI costs 78 ms of CPU and a 34 MB process each time (56 CPU-s an hour), Direct 5 ms; latency is the same 1.4 s, as GitHub is the cost.
- **Price of Direct:** `ureq` is a new dependency (`docs/implementing.md` says Jobs may not add one without the User): +26 crates (22 new to `Cargo.lock`), +2.9 MB of binary, +14 s of clean build. New contract text: an error code for a direct call (e.g. `github_failed` with kinds `network`, `auth`, `rate_limited`, `query`, `unavailable`) beside `gh_failed`; a poll timeout of its own (15 s); the token rule (read once with `gh auth token`, re-read once after a 401, never logged).
- **Price of staying on the CLI:** no new dependency or error code (`gh_failed`, exit 1, text in `stderr`), but 720 forks an hour of a 34 MB Go binary, text-matching on stderr for 401/403/504/rate limit, `gh.rs` must parse stdout despite a non-zero exit for partial results (failure 9), a 60 s `TIMEOUT` that must become shorter for the poll, and `-F` (not `-f`) for the query file.
- **Either way:** `-F query=@file` / `Bearer`, space polls by "5 s after the last one ended", read `remaining` from the poll's own response (A10), treat an empty or non-JSON body as an error, treat "state `OPEN` but absent from the search" as unknown, expect `FAILURE` while checks still run, and give an unknown search qualifier a test (it returns 0 silently).
