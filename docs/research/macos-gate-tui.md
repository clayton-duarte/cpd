## Clusters

### C1 `path-length` (182 tests, A fail / B pass; the harness is shared with every area)
- Cause: the private server's socket is `$TMPDIR/gate-run.<id>/cpd-test-<id>/tmux/tmux-<uid>/cpdt-<pid>-<n>` (`cli/tests/common/mod.rs:632` the dir under `envs_dir()`, `:634-637` the socket name, `:749` `TMUX_TMPDIR = root/tmux`). 107 characters here, 115 after tmux resolves `/var` to `/private/var`, about 121 with `GATE_RUN` in the name (`cpdt-<run>-<pid>-<n>`, `:235`): over the 104 bytes of `sun_path`. Checked by hand: `tmux -L <that name> new -d` prints `error connecting to /private/var/…/cpdt-12345-0 (File name too long)`, exit 1. In A every `cpd` command that talks to tmux answers `tmux_failed … File name too long`.
- Fix (one Job; dedupe with the other areas' triage Jobs, it is one change): a method `TestEnv::tmux_tmpdir()` in `common/mod.rs`: `root/tmux` when `canonicalize(root)/tmux/tmux-<uid>/<socket>` is at most 100 characters (all Linux runs: unchanged), else `/tmp` (socket `/tmp/tmux-<uid>/cpdt-…`, where `scripts/gate-run.sh` already scans). Use it at `:749` (`command()`), in `teardown.sh` (`:163` glob `"$dir"/tmux/*/"$socket"` and `:167,170,173` `TMUX_TMPDIR="$dir/tmux"`: pass it as a variable next to `socket`, and `rm -f` the socket file at the end of `teardown()`), and at the two other users of `root().join("tmux")`: `cli/tests/session/host.rs:26`, `cli/tests/tooling/harness.rs:95`.

### C2 `test-assumption`: the pane's PATH is rewritten by zsh (34 tests; the popup tests)
- Tests: `tui_tree` (25), `tui_widgets` (5), `tui_tree_delete` (2), `tui_tree_archive_manager` (2): the views time out on `1 popups: got []`, `copy 1 of …`, `the popup`, `Archive: No tmux client is attached to the cockpit.` (`common/mod.rs:463:77`, `:360:63`).
- Cause: the test starts the view with `new-session … '<cpd> tui view tree'` (`tui_tree.rs:267-285`). tmux runs a pane command with `default-shell` = `$SHELL` = `/opt/homebrew/bin/zsh -c`; `TestEnv::command` keeps `ZDOTDIR` (the drop list `common/mod.rs:735-741` has no `ZDOTDIR`), and the User's `$ZDOTDIR/.zshenv` rebuilds `PATH`, so the pane's PATH no longer has `env.bin()` first (dumped from a pane: `PATH=/Applications/Visual Studio Code.app/…:/opt/homebrew/bin:…`). The view's `tmux list-clients` then runs the real tmux, not the fake that answers `list-clients`/`display-popup` (`tui_tree.rs:476-491`): `No tmux client is attached`. Not a product bug.
- Evidence: `env -u ZDOTDIR` the 34 tests: 33 pass, 1 fails (C3). `SHELL=/bin/sh`: 6 of 6 tried pass.
- Fix (1 Job, with C1, same file): add `ZDOTDIR` to the vars `command()` removes (`common/mod.rs:735`). No effect on Linux where it is unset. Alternative, also verified on 6 tests: `.env("SHELL", "/bin/sh")` in `command()` (deterministic shell; changes the Linux pane shell).

### C4 `macos-code`: `/proc/<pid>/exe` (10 `bare` tests)
- Tests: see the table. Four print `Cannot find the tmux server's own binary /proc/<pid>/exe: No such file or directory` (`bare.rs:536,733,775,796`); the other six time out in a wait for the attach, the restart or `views to run old-cpd` (`bare.rs:151`): same cause by reading, not confirmed one by one.
- Cause (product): `core/src/host/tmux.rs:671-679` `server_exe()` builds `/proc/<pid>/exe`; used by `tmux.rs:494` `on_server_binary()` (`engine/src/watch/restart.rs:230`, the restart) and `tui/src/cockpit.rs:645` (attach with the server's own tmux); `tmux.rs:803` `program_gone()` tests `starts_with("/proc/")`. A Mac has no `/proc`. Cause (test): `bare.rs:143-146` `runs()` reads `/proc/<pid>/exe` (and `:310` says the copied tmux is the server's `/proc/<pid>/exe`).
- Fix (1 Job, maybe 2: the six unconfirmed tests may show a second cause once the first is gone): `#[cfg(target_os = "macos")]` in `server_exe()`: the path of the pid by `libc::proc_pidpath` (unverified here; `ps -p <pid> -o comm=` is not enough: it printed `sleep`, not a path, for a process started by name). A binary replaced by an upgrade has no equivalent of `/proc/<pid>/exe` (the path then names the new file): keep the `metadata` check so a missing file is still the error. `program_gone()` becomes `!p.exists()` for a program that came from `server_exe`. Same helper in `bare.rs:144` (`runs()`). Linux keeps `/proc` (cfg), so it does not change.

### C5 `test-assumption`, `SKIP-ONLY` (4 `tui_idle` tests; the symptom is a timeout)
- `tui_idle.rs:133` `usage()` reads `/proc/<pid>/io` (`rchar`, `syscw`) and `:137` `/proc/<pid>/stat`: `Os { code: 2 }`. The panic leaves `std::thread::scope` (`:175-196`) before `stop.store(true)`, so the noise thread never ends and the test hangs to the nextest limit (`TIMEOUT 90 s`), killed without `Drop` (see C8). Proposed in the same Job: set `stop` from a guard (also right on Linux).
- No macOS counter of bytes read through `read(2)` or of `write` calls: `proc_pid_rusage` has `ri_diskio_bytesread` (disk only, not cached reads) and CPU time; `dtruss`/`fs_usage` need root. The tests' claim (a view reads and writes nothing while idle) cannot be measured the same way: **SKIP-ONLY** on macOS, or a CPU-time-only assertion, which the User must decide. 1 Job.

### C6 `other` (1 test): the server exits with its last session, taking the `run-shell -b` job
- `tui_merge::the_confirm_closes_the_view_at_once_…` (`tui_merge.rs:382`, three rounds `y`/`Enter`/`click`): `timed out waiting for <how>: pr merge to start`; alone 1 of 3 passes, the failing round differs each time. The recorded tmux calls show `run-shell -b cpd tui action merge …` and then `has-session`; the fake `cpd` is never called.
- Cause (consistent, run-shell not traced in tmux): the view is the only session of the private server (`start_on`, `tui_merge.rs:154-158`); when it exits the server exits (exit-empty) and the pending job is lost. The real cockpit has other sessions, so no product change. Evidence: with `env.tmux(&["new-session","-d","-s","keep","sleep 600"])` before `start_on` runs, 3 of 3 pass (tried, reverted).
- Fix (1 small Job, in the C1/C2 Job): that line in `start_on`. Linux unchanged (an extra session).

### C7 `load-flake` (5 tests)
`tui::{4 tests}` and `bare::it_removes_an_older_cpds_statusbar_pane` fail in B (load 69-94, 3 of them `TIMEOUT` at the 90 s nextest limit, the rest a `wait_until` poll limit `WAIT` = 30 s, `common/mod.rs:347`) and pass 3 of 3 alone (load 3-7). Nothing to fix; they need the machine slot.

### C8 harness reaper does not work on macOS (no failing test of its own)
`common/mod.rs:198` `exec setsid sh …`: there is no `setsid` on macOS, and `alive()`/`mine()` read `/proc` (`:123,128`), so `watch` ends at once without tearing down (inferred from the code; seen: each pass left 4 `cpd-test-*` dirs and tmux servers, those of the 4 timed-out C5 tests, which I removed by hand). A test killed by the Gate's timeout therefore leaves files in `TMPDIR`, which `gate-run.sh` fails the run for. Fix (1 Job): `alive` by `kill -0` and `ps -o stat= -p`, `mine` by `ps -E -p` (unverified), and start the reaper's second stage without `setsid` (a `process_group(0)` spawn from Rust, or `perl -MPOSIX -e setsid`).
