# The webui host-socket / WebSocket path, and the cpd and pi SDK exposure: an audit

Sources: `docs/research/web-socket-audit-measurements.md` (all numbers); `pi/durable-host/protocol.ts`, `pi/durable-host/cursor.ts`, `pi/durable-host/ring.ts`, `pi/durable-host/server.ts`, `pi/durable-host/main.ts`; `web/src/api/live-server.ts`, `web/src/api/host.ts`, `web/src/api/live.ts`, `web/vite.config.ts`, `web/README.md`; `docs/architecture/sdk.md` and sibling architecture files; pi's own `rpc.md`/`sdk.md` (1.3.0 release tree).

Status: this is a research document, not a contract. It audits the webui host-socket / WebSocket path and the cpd and pi SDK exposure as the code stands, faithful to the evidence: every protocol/SDK/code claim cites `path:line`, every number cites `docs/research/web-socket-audit-measurements.md` (or is labelled `unmeasured`), and the open questions are named as questions, not decided. It is input for the bridge Workflow; nothing here is implemented.

## 1. The host socket protocol vs webui needs

The durable host speaks NDJSON over a unix socket: one JSON object per line, UTF-8, LF-terminated (`pi/durable-host/protocol.ts:251-253`, `encode()`; `web/README.md` "Framing"). One host process serves exactly one Session — `welcome` carries its `session` id and role (`pi/durable-host/protocol.ts:83`; `ServerDeps.session`, `pi/durable-host/server.ts:20`), and a non-`root` `attach.conversation` is refused `unsupported` (`pi/durable-host/server.ts:119-123`).

**Client → host** (`ToHost`, `pi/durable-host/protocol.ts:39-53`): `hello` (protocol negotiation, `:40`), `attach` with an optional `cursor` (`:41`), `submit` — text plus `when_busy: "followUp" | "steer" | "reject"`, an optional `request_id`, and up to 4 images totalling 786 432 bytes, png/jpeg/gif/webp (`:42`; `HISTORY_*`/`IMAGE_*` constants `:17-21`), `compact` (`:43`), `configure` — model and thinking level (`:44`), `list_models` (`:45`), `fork` (`:46`), `history` — paged by `before`/`limit` (`:47`), `abort` (`:48`), `abort_submission` (`:49`), `ping` (`:50`), `detach` (`:51`), `reload` (`:52`), and `ui_response` — the answer to a held UI request (`:53`).

**Host → client** (`ToClient`, `pi/durable-host/protocol.ts:82-99`): `welcome` (`:83`), `attached` with `mode: "snapshot" | "resume"`, `from_seq`, `head_seq`, `client_id` (`:84`), the stream frames `snapshot`/`events` (`:85-86`), `result` (`:87`), `error` with one of 15 `ErrorCode`s (`:88`; `:23-28` — `protocol_mismatch`, `hello_timeout`, `bad_frame`, `frame_too_large`, `unknown_type`, `bad_args`, `not_attached`, `busy`, `unsupported`, `storage_failed`, `shutting_down`, `internal`, `refused`, `hello_required`, `ui_unknown`), `host_state` — state, clients count, held-UI count, agent (`:89`), `ui_request`/`ui_resolved` (`:73-81`, `:95`), `notice`/`status` (`:96-97`), `pong` (`:98`), and `bye` — reason plus `reconnect: boolean` (`:99`).

**The stream and its cursor** (`pi/durable-host/ring.ts`): the base `snapshot` frame is seq 1; each commit appends an `events` frame at `head + 1` (`ring.ts:18-21`). `attach(cursor)` resumes iff the cursor's epoch matches and its seq sits inside the current base..head window, replaying exactly the frames after it; otherwise the client gets the full snapshot replay (`ring.ts:26-34`). The client's `Cursor` is `{epoch, seq}` (`protocol.ts:11`). Rebase folds the accumulated `events` frames into a fresh `snapshot` frame at `head + 1` while keeping the epoch (`ring.ts:41-45`), so a pre-rebase cursor falls outside the window and correctly forces a full snapshot.

**Limits** (`LIMITS`, `pi/durable-host/protocol.ts:2-8`): client line 1 048 576 B, host line 67 108 864 B, slow-client buffer 8 388 608 B, hello timeout 5 000 ms, rebase thresholds 256 frames at run end / 4 096 hard. The server enforces them all: oversized client lines are answered `frame_too_large` and dropped (`pi/durable-host/server.ts:210-216`); a client whose send buffer exceeds `slowClient` gets `bye slow_client, reconnect: true` and is dropped (`server.ts:52-57`); a connection that has not sent `hello` within `helloMs` is dropped `hello_timeout` (`server.ts:199-204`).

**Attach replay order** (`pi/durable-host/server.ts:117-131`): `attached` frame, then the ring's frames (base + events in snapshot mode, or just the missed events in resume mode), then every held UI request replayed with `replayed: true` (`server.ts:126-128`), then one `host_state`. The reader is caught up when it has applied the frame whose `seq` equals `attached.head_seq` (`web/README.md`, §6.20's rule).

**What a webui gets, and what it does not.** The protocol already carries everything a chat surface needs: a resumable transcript stream, send (`submit` with the three `when_busy` modes), abort (run and submission), compact, configure + `list_models` (a model picker), `fork`, paged history (`HISTORY_LIMIT` = 50 per page, `HISTORY_MAX` = 500, `protocol.ts:17-18`), and the held-UI round trip for approvals and questions. What it deliberately does **not** carry: any multi-session view (one socket, one Session), and any keying into the cpd ledger — Sessions, Plans, Jobs and the Inbox live in `$CPD_HOME/cpd.db` (`docs/architecture/sdk.md`, "Ledger"; verified 2026-11-01 19:26 EST: `/home/clayton/.cpd/cpd.db` exists, 198 541 312 bytes, SQLite 3.x, `user_version` 1000), reachable today only through the CLI's commands.

## 2. The bridge shape

The dev adapter is the only bridge that exists. It has three layers.

**Browser → dev server (HTTP SSE, not WebSocket).** `LiveApi` (`web/src/api/live.ts`) speaks six routes: `GET /__cpd/sessions`, `/__cpd/inbox`, `/__cpd/plans`, `GET /__cpd/sessions/<id>/transcript` (paged, `live.ts:89-100`), `GET /__cpd/sessions/<id>/frames` (SSE, `live.ts:79-87`), and `POST /__cpd/sessions/<id>/send` (`live.ts:103-108`). The token travels as the `x-cpd-token` header on fetches and in the `?token=` query on the EventSource, because an `EventSource` cannot set headers (`live.ts:79-80`). Every send carries the fixed one-line reason `SEND_UNBLOCKS = "sent from the cpd web chat"` (`live.ts:10`).

**Dev server → cpd (CLI spawns).** `realDeps()` (`web/vite.config.ts:69-158`) wires every read and the one send as `execFile` calls of the cpd binary (`vite.config.ts:24`): `session list --role lead --role manager` (`:75`), `session show <id>` for the pi file path (cached per id), `session tail <id>` (`:121`), `session send <id> <text> --unblocks <reason>` (`:124`), `inbox list`, `plan list` (archived rows skipped). The frames stream (`web/src/api/live-server.ts`) polls: for a pi Session one `fs.stat` per `POLL_MS` = 1000 ms tick (`live-server.ts:83`, `:259-268`), re-reading and re-parsing the whole JSONL on an mtime change; for a durable Session it re-runs `readDurable` each tick and re-sends when the messages change (`live-server.ts:270-283`). The snapshot it sends is the newest 40 turns within a 1 000 000-byte budget, the newest turn always kept (`SNAPSHOT_TAIL`/`SNAPSHOT_BUDGET_BYTES`, `live-server.ts:90-119`), folded by the client through the existing fold (`web/src/fold/fold.ts:49`; `SnapshotFrame` `:25-31`).

**Dev server → host socket (the read-only client).** `createHostClient` (`web/src/api/host.ts:57-164`) is the socket reader: path `$CPD_HOME/run/host/<id>.sock` (`host.ts:53-55`), one connect + `hello` (protocol 1, `host.ts:40`) + `attach` with the saved cursor per `attach()` call, frames out, reconnecting per the README rule — 100 ms doubling to a 1 s cap over a 30 s deadline (`host.ts:36-38`, `:69-73`). It never sends a write (`host.ts:1-4`). **But it is not wired:** `realDeps()` has no `host` key (verified: `grep host web/vite.config.ts` finds no wiring), so the durable frames route today takes the `deps.tail` fallback — and `cpd session tail` follows a live host forever, never resolving (measured: `docs/research/web-socket-audit-measurements.md` §2e — 20 s, 0 bytes, exit 124). The durable transcript route has the same shape (`readDurable`, `live-server.ts:148-156`, called from `readTranscript` `:160-164`), so it hangs the same way through the real wiring — a code-path inference, consistent with the §2e measurement of `tail` itself.

Two consequences of the allowlist in `host.ts`: `ALLOWED_FRAMES` (`host.ts:42-51`) admits `welcome`, `attached`, `snapshot`, `events`, `host_state`, `error`, `bye` — and excludes `ui_request`, `ui_resolved`, `notice`, `status`, `result`. The server replays held `ui_request` frames at attach (`pi/durable-host/server.ts:126-128`), so a client built on today's allowlist would silently drop a held approval. Widening the allowlist (or the `HostFrame` type, `host.ts:11-28`) is required before the bridge can surface held UI.

## 3. The cpd SDK

The architecture names the SDK as core + ledger + engine (`docs/architecture/sdk.md`), and the interfaces rule as CLI-first: every capability is a command, one JSON value on stdout (`docs/architecture/interfaces.md`; contract §1.1). The dev adapter lives entirely inside that rule — every cpd interaction is a CLI command (`web/vite.config.ts:69-158`), and each call costs a fresh process spawn: `session list` median 16.27 ms, `session show` median 13.57 ms (`docs/research/web-socket-audit-measurements.md` §4), ~34–180× a socket round trip.

The ledger is one SQLite database per machine, written under single-writer discipline: one engine per machine plus short-lived CLI transactions, and a process that is not cpd cannot write it — triggers call `cpd_txn()` (`docs/architecture/sdk.md`, "Ledger"). So a webui bridge can read the ledger directly for its lists, but its writes must go through cpd: either a CLI command (today's send path) or a socket `submit` into the Session's host, whose adapter writes through the core.

What the bridge can rely on from the SDK's shape: every read the adapter performs is already a command (`session list/show/tail/send`, `inbox list`, `plan list`), so no capability needs inventing; and the production `cpd web` shape decided for the web UI (`cpd-web` crate, tiny_http-class server, live views over WebSocket, unix socket behind `tailscale serve`; `docs/architecture/interfaces.md`, "The web UI (in flight)") can embed cpd-core the way the durable host embeds the pi SDK — reading the ledger through core and writing only through core.

## 4. The pi SDK

pi ships two integration surfaces (1.3.0 docs):

- **The SDK** (`@earendil-works/pi-coding-agent/docs/sdk.md`): in-process `createAgentSession()` — the session owns the conversation, model, tools, queued messages, compaction and extension runtime; `prompt()`/`steer()`/`followUp()`/`abort()`/`waitForIdle()`; event subscription delivering `message_update`, `message_end`, `agent_end`, `agent_settled`; `SessionManager` (persistent or in-memory) and `AgentSessionRuntime` (`newSession`, `switchSession`, `fork`, `importFromJsonl`); `ModelRuntime`; extensions loaded through `DefaultResourceLoader`, with `codemode`/`tool_search`/MCP as explicit factories in SDK sessions; `dispose()`.
- **RPC mode** (`docs/rpc.md`): a subprocess (`pi --mode rpc --no-session`) speaking JSONL on stdin/stdout — commands correlated by `id`, `prompt` dispositions `started`/`queued`/`handled`, settle on `agent_settled`, stdout reserved for protocol records, stderr for diagnostics, stdin closed for an orderly shutdown. The docs warn that Node's `readline` splits on U+2028/U+2029, valid inside JSON strings — a framing trap.

**How cpd uses it:** the durable host embeds the SDK in-process, not RPC mode. `pi/durable-host/main.ts:25-46` wires `ModelRuntime.create({ refreshOnCreate: false })`, `resolveCliModel`, a `models()` mapping `getAvailable()` to `{provider, model_id, name, thinking_levels, context_window}`, `loadProjectContextFiles`, `openConversation` from the durable-worker harness, and the `Follower` — the commit watcher whose events become the `events` frames the ring broadcasts. The host then exposes its own NDJSON protocol (§1) over the unix socket via `guardSocket`/`listenOn` (`main.ts:45-46`). pi's RPC mode is unused by cpd today.

**Implication for the bridge:** the webui never needs pi's SDK or RPC directly. A durable Session's live stream already reaches the socket (§1); a pi Session's transcript is a JSONL file read — `parsePiSession` in `web/src/transcript.ts`, a file-format read, not SDK exposure. If the bridge ever wants streaming deltas for pi Sessions, the pi SDK (in-process) or RPC mode would be the route; nothing in this audit requires it.

## 5. Performance, measured

All numbers are from `docs/research/web-socket-audit-measurements.md`, measured on hs 2026-11-01 (times EST, zone stated there); each bullet cites its section.

- **Handshake** (§1): connect + `hello` → `welcome` median 0.50 ms (min 0.39, max 1.93 over 25 reps; one cold-start rep at 33.05 ms in the earlier run); `attach` → first `snapshot` median 0.14 ms; the snapshot is 338 bytes. Full handshake-to-transcript under 1 ms warm.
- **Idle behaviour** (§2b): an attached client receives zero frames in 30 s of idle — the host pushes only on change; the attach burst (`attached` + `snapshot` + `events` + `host_state`) lands within 0.6 ms of the attach write.
- **On-channel round trip** (§2c, §4): one `ping`→`pong` on an established hello connection, median 0.09 ms (max 1.62); a fresh connection's `hello`+`ping`→`pong`, median 0.49 ms (max 2.24). This is the per-message latency floor of the socket path.
- **Pi poll tick** (§2d): an unchanged tick is one `fs.stat`, median 0.020 ms — noise against `POLL_MS` = 1000. A changed tick on the largest pi Session (29 626 897 bytes) costs read 80.6 + parse 127.2 + tail+stringify 1.3 = 209.1 ms and emits one 185 649-byte frame: ~0.2 CPU-seconds per change, inside the same 1 s tick loop.
- **Durable tick through the real wiring** (§2e): `cpd session tail` against a live host never returns (20 s, 0 bytes, exit 124). The adapter's durable frames route is therefore a hang today, not a number; the host-socket read would cost the §1 handshake per tick.
- **Frames route on an idle pi Session** (§5): one snapshot at stream open (90 675 bytes), then zero writes and zero keep-alive bytes in 60 s; 60 stat calls totalling 7.71 ms (≈0.013% of the interval).
- **CLI spawn** (§4): `session list` median 16.27 ms (19 617 B out), `session show` median 13.57 ms — one CLI call costs ~34–180× a fresh-connection socket round trip and ~180× an on-channel round trip.
- **Snapshot sizes** (§3): the 40-turn tail frames measure 122 901 / 185 649 / 187 642 bytes for Sessions of 4.13 / 29.63 / 16.49 MB; the 1 MB budget never engaged, so frames are turn-count-bound at 40. Whole transcripts as one event would be 4.1–29.6 MB — above the sizes Chrome's `EventSource` is known to drop (cited from `web/src/api/live-server.ts:84-97`'s comment, measured there 2026-11-01: 4/8/20 MB events never fired `onmessage`; 1/2 MB did).
- **Every measured frame is far under `clientLine`** (1 048 576 B, `protocol.ts:3`): the largest, 187 642 B, is 0.18 of it.

## Verdict

1. **The protocol is sufficient; the bridge is wiring, not protocol.** `ToHost`/`ToClient` already carry everything a chat surface needs — resumable transcript, send with the three `when_busy` modes, abort, abort_submission, compact, configure + list_models, fork, paged history, held-UI round trip, host_state. No protocol extension is needed for the bridge Workflow.
2. **The dev adapter proves the read and send paths end to end, but its durable read is mis-wired.** The send path works (CLI spawn, fixed reason); the pi frames path works (mtime poll + full re-read). The durable frames route hangs today because `realDeps()` wires no `host` read (`web/vite.config.ts` — verified absent) and the `tail` fallback never returns against a live host. Wiring `deps.host` through `createHostClient` is the one change the measurements already bound at sub-millisecond cost per tick.
3. **The poll is the dev cost; the push is the bridge shape.** A 1 s mtime poll with a full 29.6 MB re-read per change (209 ms) is fine for a dev window. The production bridge should attach once per client and let the host push: the host pushes only on change (§2b), the on-channel round trip is 0.09 ms (§2c), and the fold (`web/src/fold/fold.ts`) already consumes `snapshot`/`events` frames with cursor resume.
4. **The send path upgrades for free.** Today's send spawns a CLI process (median 13.57–16.27 ms, §4) and always posts the fixed reason. Over the socket, `submit` is one frame — median cost the §1 handshake — and `when_busy` gives the real follow-up/steer/reject choice instead of a fixed string.
5. **One host, one Session.** A webui listing many Sessions opens one socket per live durable host; pi Sessions remain a file read. The session list itself is a ledger read, reachable only through the CLI today — a `cpd web` process embedding cpd-core (the decided production shape) would replace those spawns.
6. **The allowlist gap is real but small.** `host.ts`'s `ALLOWED_FRAMES` drops `ui_request`/`ui_resolved`/`notice`/`status`/`result` — including the server's held-UI replay at attach (`server.ts:126-128`). The bridge must widen the allowlist and the `HostFrame` type before it can surface held approvals.
7. **SDK exposure stays as decided.** The webui is a client of the core (`docs/architecture/interfaces.md`); the durable host embeds the pi SDK in-process and speaks the §1 protocol; pi's RPC mode is unused and unneeded. The bridge reuses exactly this — no new pi surface.

## Not measured

- **Per-event push latency** from a host state change to the pushed `events` frame: needs a `submit` into a live Session — forbidden (no message to, no `submit` into, any live Session; User decision hs-d839). The reachable floor is the on-channel ping→pong, 0.09 ms median (§2c).
- **A real `submit` round-trip time** (agent wake-up to first frame): same prohibition. Unmeasured; ask the Lead if the bridge needs it.
- **`clientLine` against real pi-session line sizes**: the largest single JSONL line in the measured files was never computed; no limit-approaching line is known (`docs/research/web-socket-audit-measurements.md` §6).
- **EventSource drop thresholds**: cited from `web/src/api/live-server.ts`'s comment (measured there on Chrome, 2026-11-01), not re-measured here — a browser is needed.
- **Multi-client fan-out** (broadcast cost at `clients: N`, fan-out latency): one client at a time only.
- **`helloMs` timeout behaviour** (5 000 ms): not exercised.
- **Reconnect/back-off cost** (`host.ts:36-38`, 100 ms→1 s cap over a 30 s deadline): not exercised — it needs a host socket to disappear.
