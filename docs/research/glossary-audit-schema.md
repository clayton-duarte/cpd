### Decisions needed (mixed rows), with a proposal

The User decides; these are proposals and why.

- **`pr open`, `pr rebase`, `pr push`, `pr view` (CLI).** They take a Workflow key and act on its Lead Branch and its pull request. Proposal: move all of `add edit describe cancel start open rebase push view` under `cpd workflow`, keep `poll post reply merge` under `cpd pr` (they act on the pull request, as the Spec says). Why: the noun is the thing the command takes as its argument; `open` takes a Workflow key.
- **`pr-opened`, `pr-merged` Events.** Both a Workflow and its pull request are opened or merged; the data carries the Workflow key and the pull request number. Proposal: `workflow-opened`, `workflow-merged`, because the status that changes is the Workflow's (`prs.status`), and the number is data. Why: the Events already say `pr-started`, `pr-cancelled` (Workflow only), so one prefix per object keeps the kinds sortable.
- **`--pr` flag.** `--pr <key>` becomes `--workflow <key>`; `cpd review submit --pr <url>` keeps a name that says a pull request. Proposal: `--pull-request <url>` there (or keep `--pr`, which then means only the pull request). Why: one flag, one sense.
- **Policy domain `[pr]`, `gate.pr`, `pr.post.*`, `pr.feedback.*`, `pr.jira_required`, `[pr] gate` alias, role section `pr`.** They are about opening and following the pull request; only `pr.jira_required` and the ticket concern the Workflow. Proposal: keep `[pr]` as the pull request domain (its sense stays `pull request`), move `jira_required` to a `[workflow]` domain if the User wants it, and delete the deprecated `[pr] gate` alias rather than rename it. Why: policy files exist on this machine (`~/.cpd/policy/**/owner.toml`) and a rename is a rewrite of User files.
- **Error codes `pr_adopted`, `pr_closed`, `pr_not_closed`, `pr_not_open`.** Raised on Workflow keys about the state of the pull request. Proposal: `workflow_adopted`, `pull_request_closed`, `pull_request_not_closed`, `workflow_not_open`, after reading each raise site (unverified here).
- **Table `pr_posts`.** Posts the pull request but is keyed by `(plan, pr)`. Proposal: `pull_request_posts` with column `workflow`.
- **Helper names on the pull request** (`merge_pr`, `create_pr`, `close_pr`): keep (they run `gh pr`); `describe_pr` becomes `describe_workflow`.

### What is stored, and what needs a protocol bump

- **Needs a migration (new, never an edit of an applied one):** tables `prs`, `pr_needs`, `pr_posts` (maybe), columns `jobs.pr`, `pr_needs.pr`, `pr_posts.pr`, `slack_reactions.pr`, `incident.until_pr`; hand-written triggers `prs_locked`, `prs_status`, `prs_shape_fixed`, `prs_head_ref_fixed`, `pr_needs_locked`, `pr_needs_no_delete`, `jobs_pr_dependencies`, `dependencies_same_pr` and the index `prs_head_ref_live`; `history_tables.name` rows; `history.tbl` values (prs 1058, pr_needs 218, pr_posts 8 rows); `event_kinds.name` rows and `events.kind` values for the renamed kinds (history may stay: Events are history, but then the reader accepts both kinds, which the no-alias rule forbids, so the Events are rewritten: unverified decision).
- **Needs the pi protocol bump (`PROTOCOL` 17 → 18 in `core/src/events/kind.rs:38` and `pi/lib/event.ts:9`):** every renamed Event kind (`KINDS`), the Event data keys the adapter reads (`pr`, `number`, `url` of `pr-opened`), and the `plan show` JSON keys `prs` and `pull_request` the adapter parses (`pi/lib/updates.ts:140-151`, outside the part).
- **Locked, fingerprinted or hashed (contract §2.3, §4.3):** the plan fingerprint is `sha256` of the JSON `{jobs, prs}` where each Job has the key `pr` and each PR `{key, repo, base, needs, shape}` (`core/src/plan/fingerprint.rs:15-70`, outside the part). Renaming the keys `pr` and `prs` changes the fingerprint of every stored `plan_reviews` row (112 rows) and the 1409 non-null `jobs.fingerprint` values, so every stored Plan review would stop being current: a rename of those two JSON keys needs either a fingerprint of the old shape kept for old reviews or a re-review (decision for the User). The migration checksums (`schema_migrations.checksum`) hash the SQL text, so applied files never change. The triggers `prs_locked`, `pr_needs_locked`, `jobs_locked` forbid changes of the Locked columns (`repo`, `base`, `needs`, `jobs.pr`) after the Plan lock: a migration that renames them must run with the triggers dropped, like the legacy rebuilds (`0004`, `0006`, `20261102T1000`).
- **Branch and worktree names** carry the Workflow key and the Plan id but not the word `pr`; 295 `prs.lead_branch` and 207 `prs.lead_worktree` values are stored and git directories exist on this machine; nothing about them changes by a word rename.
- **Free text in the store** that says PR: `events.text` (3770 live Events mention `PR ` or `pull request`), `jobs.cancel_reason`, `jobs.*` titles and Specs, `context_records`. These are history and keep the old words.
