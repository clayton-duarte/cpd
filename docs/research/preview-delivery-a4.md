## Source, build, activation and verification

1. **Source integration (isolated only):** create a separate worktree based on the local `preview/web` commit on a *new* branch, not `preview/web`; integrate the complete #969 commit and the regression/report commits, or use a reviewed branch containing them, resolve conflicts and run the targeted tests. The fixture demonstrates the web source patches apply, not that cherry-picking the full commits or an eventual merge is conflict-free. The branch cannot be obtained from an absent remote `preview/web`. `scripts/preview-web.sh serve` and `on` create `preview/web` from `origin/main` only if the requested directory is missing; an existing checkout is left in place. Neither operation merges these commits into the existing Preview. Updating files in a worktree currently served by Vite risks HMR immediately, before an explicit activation. A separate unserved fixture does not touch live drafts; preservation of a live draft while changing the served checkout is **unverified**.
2. **Build (isolated only):** install pinned dependencies in the isolated worktree (`pnpm install --frozen-lockfile`), run `pnpm --filter cpd-web-client run typecheck` and `pnpm --filter cpd-web-client run build:electron`, check the renderer, main and preload files above. These are the package's supported build commands; the fixture build above used equivalent direct Vite targets, not the pnpm wrapper. Do not point a build at the user's checkout. An isolated build does not navigate the live app; preservation if building in the served checkout is **unverified**. The in-place Preview renderer is Vite, so a built bundle alone is not evidence it is running.
3. **Activation (requires separate authorization):** source `web/src/electron/main.ts` resolves `CPD_WEB_PREVIEW_WORKTREE` or the default sibling path, calls `ensurePreviewClient`, and `preview-client.ts` runs `scripts/preview-web.sh serve <worktree>` before loading `CPD_ELECTRON_DEV_URL` or `http://localhost:5173/electron.html`. `serve` can respawn the `web` tmux pane and the View switch loads a new page; `on` also runs a watchdog; `reload` typechecks/builds then sends SIGUSR1. These are supported interfaces, **not draft-safe activation guarantees**, and are not interchangeable. Changing environment variables of a future process does not retarget an already-running Electron process. No activation was performed. Only after preservation is independently confirmed and the User authorizes disruption may the operator choose the correct supported activation for the actual running version and environment; a restart may be needed to select a different worktree, with additional draft risk.
4. **Live verification (not established safely):** `scripts/preview-web.sh status` reports its `web-state`, not the in-place `serve` client, actual page origin, or served source/build identity. A checkout's `git rev-parse HEAD` is not proof of the bytes loaded in Vite, particularly with dirty files, HMR and watchdog restore. Existing `ui-view.json` is a mode marker, not proof of origin/version. Before activation, determine the actual loaded origin and renderer version using a supported, non-mutating inspection method; none was established. After authorized preservation and activation, independently confirm actual origin, served source/build provenance including dirty state, selected session and restored text/attachments, then exercise a failed agent tool and report pending/deduplication/success/dismissal/retry. No such live inspection or behavioral test was done, and draft preservation through it is **unverified**.

## Draft risks and escalation

Both Preview base and this Attempt's source show `Composer.tsx` initializes the session text from `drafts.ts`, saves text under `cpd-ui:draft:<sessionId>` in `localStorage`, and catches storage exceptions (text may exist only in memory). Attachments are `useState` initialized empty; they are not included in `saveDraft`. `App.tsx` stores selected plan/session in `sessionStorage` (`cpd.selection`), with restoration conditional on live cockpit state. Storage is origin-scoped; an origin change may make old text inaccessible. These source observations do not prove what the actual running renderer has stored or what HMR/reload/navigation preserves. `Composer.test.tsx` covers a mocked-storage text remount, not real renderer/origin changes, selection and attachment recovery. Actual origin, exact live version, draft contents, attachment persistence and end-to-end preservation are **unverified**.

Missing mechanism: a supported, non-mutating live renderer origin and content-version/provenance inspection, plus an explicit capture/restore protocol that includes unsent text for every relevant session, current selection and the actual staged attachment bytes/metadata, acknowledges durable capture before any HMR/navigation, and verifies restoration at the destination origin/version. It must surface storage/capture failures rather than silently continuing. This is a proposed design, not an implemented or approved feature. Alternative: the User manually preserves all relevant text, selection and original attachment files, confirms they can be restored, and explicitly authorizes a disruptive activation and verification window. Copying text alone is insufficient. Either path still needs actual-origin/version verification; without it do not claim delivery. Existing sync/rebase and watchdog behavior can also replace files or reload and cannot be assumed benign.
