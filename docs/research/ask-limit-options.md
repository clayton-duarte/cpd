# Teaching an agent the `ask_user_question` limit before the call

Survey for Plan `ask-limit`, Job `survey-docs`, Attempt 1. Read 2026-10-23. Research only: no code, skill or doc other than this file was changed.

## Question

cpd's guard G2 refuses an `ask_user_question` call whose text is over 1500 characters (`pi/lib/askguard.ts:4` `LIMIT`; `textLength` at `:13-26`; applied at pi's `tool_call` in `pi/lib/adapter.ts:53-70`, the refusal at `:62-63`; contract `docs/commands.md` §15.13 at line 3648). Leads and Managers learn the number only by hitting the refusal. Which way does pi offer to teach a tool's input limit **before** the call, which does the pi community recommend, and how would each be done in cpd's adapter, with `LIMIT` as the single source of the number?

Facts checked here that the Job spec stated differently or not at all:

- The number is **not** only in `references/questions.md`: `pi/skills/cpd-lead/SKILL.md:29` and `:102`, `pi/skills/cpd-manager/SKILL.md:32` and `pi/skills/cpd-lead/references/questions.md:48` all contain "1500", and `pi/skills/skill.test.ts:727` pins `/enforces G2.*1500-character limit/`. A skill body is not in the system prompt: pi lists only name, description and location, and the agent must read the file (`dist/core/skills.js:278-303`, pi 1.3.0). Whether the Lead or Manager reads it before an ask is unverified.
- The installed `@juicesharp/rpiv-ask-user-question@2.13.8` has no total limit anywhere (`tool/types.ts:40-70`: `maxLength` on `label` 60 and `header` 16 only; `maxItems` 4 on options and questions). G2's total is cpd's rule, not the package's.
- cpd's own `askguard.test.ts:11` restates `1500` as a literal on purpose (it pins the contract), so a changed `LIMIT` breaks it; that is a test, not drift.

## How cpd would do the top three

All three build their text from one new exported function in `pi/lib/askguard.ts`, next to `LIMIT` and `longReason`, so the number is read, not restated (DRY, `askguard.ts:4,7-8`):

```ts
export const limitNote = (): string =>
  `ask_user_question: the whole call may hold at most ${LIMIT} characters, added up over every question, header, option label, description and preview; a longer call is refused before the User sees it. Keep it to a few short choices; put anything larger in plannotator.`;
```

(Proposed wording, not tested on a model.) The words "refused before the User sees it" match G2's own reason text.

### Option 5: a prompt section from `before_agent_start` (Worker's first choice)

- Where: the existing `before_agent_start` registration in `pi/lib/agent-state.ts:29-42` (or a sibling in `adapter.ts`), which already sets `sections[POLICY_SECTION]` and reports a missing `sections` once.
- What: `sections.ask_limit = limitNote()` when `host.run?.info.role` is `lead` or `manager` (the role is read per call, as at `adapter.ts:54`); a Worker has no such tool (`commands.md` §15.13 "Not affected"). Section names must match `^[a-z][a-z0-9_-]*$` (`system-prompt.js:7,72-75`), so `ask_limit` is valid; pi wraps it as `<ask_limit>…</ask_limit>` (`:118`).
- The model sees: the sentence above, in every run, inside `<ask_limit>`.
- Test (pins the contract, not the code): extend the `sectionsAfterStart` pattern of `pi/test/policy.test.ts:9-16`: a Lead and a Manager get `sections.ask_limit` equal to `limitNote()` and the text contains `String(LIMIT)`; a Worker gets none; `longReason(1)` contains `limit ${LIMIT}` (so both messages cannot disagree). It cannot rot: the test imports `LIMIT`, and `askguard.test.ts` already pins 1500.
- Cost: system-prompt tokens per run (about 60 words); advisory (a model can still ignore it, G2 stays). Drift: none (cpd's text). Sync: none beyond `LIMIT`.

### Option 9 (prepareLoadout): append to the tool's own description

- Where: a small tool registered from `pi/lib/startup.ts` next to `registerTool(host)` (`startup.ts:193`; the adapter already registers `cpd_plan_review` in `review.ts:238-241`), with `prepareLoadout`.
- What: `prepareLoadout: (l) => { const t = l.declared.find((x) => x.name === "ask_user_question"); return t ? { descriptions: { ask_user_question: `${t.description}\n\n${limitNote()}` } } : undefined; }`. It **merges** (reads the package's current text, appends), so a package update changes nothing for us. Pi applies it at `agent-session.js:1161-1210`.
- The model sees: the package description, then the sentence, in the tool declaration (where `read` and `bash` state their limits).
- Test: fire `prepareLoadout` with a fake loadout holding `{name: "ask_user_question", description: "D"}` and assert `descriptions.ask_user_question === "D\n\n" + limitNote()`; assert `undefined` when the tool is absent (a rename of the tool fails loudly at the second case only if the loadout is built from the installed package: load `registerAskUserQuestionTool` from `node_modules`-installed `@juicesharp/rpiv-ask-user-question` with a fake `pi` and assert the registered name and a non-empty description; unverified that the test fixture can import it).
- Cost: a cpd tool in the model's tool list for Leads and Managers (extra declaration tokens, and a model could call it); depends on a hook documented for orchestrating tools (`extensions.md:181`), so pi may change it; role gate needed (the tool is registered per session). Hiding the helper with `hiddenDeclarations: [its own name]` is a guess, unverified.

### Option 7: the rpiv `guidance` config file

- Where: a step of install or `cpd doctor` (the `lead_packages` check at `commands.md:3199` already knows the package and version) writing `~/.config/rpiv-ask-user-question/config.json`. Nothing writes it today (checked). Alternatively set `XDG_CONFIG_HOME` for Lead and Manager pi launches (`contract.md:2866` describes the launch; unverified that cpd can set env there).
- What: `{"guidance": {"description": <DEFAULT_TOOL_DESCRIPTION> + "\n\n" + limitNote(), "promptGuidelines": [...DEFAULT_PROMPT_GUIDELINES, limitNote()]}}`, with the defaults imported from the installed package (`ask-user-question.ts:347-373`, `export const`), never retyped.
- The model sees: the same sentence in the description and the guidelines.
- Test: generate the object from the installed package's exports and assert it starts with `DEFAULT_TOOL_DESCRIPTION` and ends with `limitNote()`; a `doctor` check that the file's text equals what the installed version would generate (a package update turns the check red).
- Cost: replace semantics, so the file is stale after every package update until regenerated; read once at registration (restart); the file is **global**, so it also changes the User's own pi sessions outside cpd; `XDG_CONFIG_HOME` relocation would also move every other tool's config (guess: breaks them). Needs a new install step cpd does not have.

## Recommendation

Worker's opinion, not a decision:

1. **Option 5.** It is the smallest correct change: one handler on a mechanism cpd already uses (`agent-state.ts:29-42`), text built from `LIMIT`, no coupling to the package, easy to test, easy to revert. Weakness: the sentence sits in the system prompt, not in the tool's description, where pi's own example and the community put limits, so a model may weigh it less (guess: unmeasured; `survey-baseline` is the measurement Job).
2. **Option 9 via `prepareLoadout`**, if the User wants the sentence in the tool description without waiting for upstream. It matches the community's place and merges instead of replacing, but needs an extra model-visible tool and uses a hook meant for other uses. Reasonable to add after 1 shows the sentence is not enough.
3. **Option 8 (upstream PR) in parallel**, a merge-style `guidance.descriptionAppend` or a configurable total, then option 7 only if it lands. Option 7 alone is last among the real choices: replace semantics, a global file, no installer.

Not recommended: option 4 (mutating cuts text the agent promised to state, against hs-d553), option 3 as the only measure (cannot express a total; keep G2), option 10 (the number is hs-d503's; raising it moves the refusals), option 6 (already done, in four files, and skill bodies are read on demand).

## Choices for the User

1. **Prompt section**: Recommended: add an `ask_limit` section built from `LIMIT` for Leads and Managers in `before_agent_start`; about 10 lines, no package coupling, advisory (G2 stays), in the system prompt not the tool description.
2. **Tool description**: append the limit to the package's description with a small cpd tool's `prepareLoadout`; where pi and the community put limits and it merges, but adds a model-visible tool and uses a hook documented for another purpose.
3. **Upstream first**: open a PR to rpiv-mono for a merge-style guidance key, use the section (1) meanwhile; right long-term home, but slow and not in our control.
4. **Guidance config file**: cpd writes the rpiv `guidance` file from the package's own defaults; official knob, but replace-only, global to the User's pi, and stale after each package update until regenerated.
