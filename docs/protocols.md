## The bug report protocol's tooling

Plan `protocol-enforce` brings the bug report protocol up to the definition (air-d101, air-d85), in two Workflows:

- **`bug-record`** — the bug record: `cpd protocol bug report|mitigate|close|list|show`, recording each bug and its protocol state (symptom, cause, mitigation applied by whom and when, root-fix link, regression test), so "mitigation applied: no" is a visible, queryable state (air-d103, air-d104, air-d107).
- **`bug-guard`** — the check: on the engine's periodic tick, an open bug with no mitigation past the 15-minute bound, or a recurring normalized symptom, records a structured `BugProtocolBreach` Event and alerts the owner (the Plan's Lead, else the Manager) and the User (air-d105, air-d106).

No other protocol is being tooled yet. The audit found further gaps for the other protocols; follow-up Workflows for them are planned by the Lead and to be ranked with the User (Plan `protocol-enforce`'s requirement 3) — none is registered yet. The refusal Events, metrics and alerts machinery they build on is Plan `agent-refusals` (air-d81).

## Guarded rules that are not protocols

The registry is complete at the six above. Rules that are guarded but are not User-invoked procedures — the primary-checkout rule (pi/lib/mainguard.ts), a Worker's refused full test runs (pi/lib/testguard.ts), a Manager's or Lead's refused waits over 30 seconds (pi/lib/noblock.ts), the loop guard (pi/lib/loop-guard.ts), and the `agent_forbidden` and explore-submit refusals (contract §1.2) — are not protocols in this sense. None of them logs its breach; that is Plan `agent-refusals`' scope.
