# WebUI trusted human ingress — proposed design (review required)

Status: design proposal only. No mitigation is implemented or enabled. This is not authorization to clear loop-guard state. Air-d137 requires authentication, session-target binding, and correlated delivery outcomes before WebUI loop-guard recovery; user review is required for unresolved security choices.

## Evidence and boundary

The inspected implementation has no authenticated principal: `web/src/server/ws.ts` accepts absent/`null`/`file://`/loopback Origin and defaults to loopback binding; Origin is not authentication and local non-browser clients can omit/forge it. `web/src/server/hub/connection.ts` resolves client-selected session IDs and enforces subsequent connection-to-session consistency (`not_attached`), but performs no principal-to-session authorization. `web/src/server/pi/backend.ts` adds `--origin webui`, a surface marker, not identity. `docs/contract.md` §§5.5, 6.13–6.15 and 15.15 document current input/delivery and guard behavior; notably `reply: true`/`cpd-chat` are not proof of a human. Scout evidence: `$CPD_HOME/run/desktop-shell/explore/webui-trust-scout.md` (transport Origin at `ws.ts:82-101,178-190`; attachment at `connection.ts:91-126`; contract unresolved at `docs/contract.md:4959,5269`). Scout is source inspection, not penetration testing.

Trust boundary should be the privileged host/engine, not renderer, browser Origin, labels, connection IDs, or caller-provided session IDs. All local clients—including malicious processes running as the same OS user, forged frames, compromised renderer/dependencies, replaying clients, and races across multiple clients—are adversarial. Loopback only reduces remote exposure; it does not isolate local callers. OS-user compromise or theft of a bearer credential defeats a same-user boundary. No claim of protection against these is made.

## Candidate authentication and lifecycle (unapproved)

Cross-scout options from `$CPD_HOME/run/engine-defects/explore/scout-trusted-ingress-design.md` (provisional, not agreed): (A) Electron main/native broker as trusted boundary with narrow, validated renderer IPC and target authorization; (B) trusted-host-issued short-lived, scoped, one-use capability bound to principal/session/operation/nonce, atomically spent. Option A is preferable for a desktop-only trust claim if the actual main/native boundary can authenticate/confirm the human and keep credentials out of renderer. Option B can be a transport mechanism only if issuance is itself from that trusted human boundary; a host-created bearer by itself proves possession, not human identity, and is exposed if delivered to compromised renderer. Neither is verified implemented here. Browser Preview cannot rely on Electron IPC; it needs a separate reviewed authentication boundary or must not be trusted for recovery. Do not silently treat Preview as equivalent.

For either candidate: authenticate/confirm at trusted boundary; never accept renderer `isHuman`, origin label, or target as proof. Keep credential out of URL, logs and persistent renderer storage; scope to operation and exact session, short expiry, nonce/one-use, server-side atomic consume, revoke on logout/OS lock/app shutdown/restart or compromise, and fail closed. Validate IPC sender/frame and narrow methods if option A; revalidate authorization and current target at service admission and immediately before guard clear/dispatch. A fixed or renderer-readable bearer does not protect against XSS/renderer compromise; same-user malware/process impersonation may defeat process-local protections. OS login/process identity alone is not necessarily present human intent. Required assurance, Preview policy, credential issuance channel and lifecycle are User/Lead decisions.

Authenticated principal must be server-derived and immutable per connection. Authorization must independently bind principal to an explicit target session and permitted operation; attach is not authorization. Bind each request to immutable session ID, connection/principal, unique request ID, and payload digest. Engine must reject mismatched target, duplicate IDs with different payload, stale/unknown principal, and replay; stable same-ID/same-payload retry returns the original outcome, never submits twice.

## Reconciled source evidence and provisional boundary/interface (not approved)

Cross-Plan reconciliation with the merged engine-defects scout (`$CPD_HOME/run/engine-defects/explore/scout-trusted-ingress-design.md`): both agree on server-derived principal, exact target/request binding, replay-safe correlation, and an authoritative guard transition as the only recovery proof. This document incorporates the scout's later source findings; it does not select or approve an architecture.

Verified current transport: `docs/contract.md:3523` and `web/CONTRACT.md:2147` specify Electron main binds the loopback WebSocket and passes its URL through preload/contextBridge; WebUI data uses that socket, not a main-process IPC data channel. The endpoint also serves browser Preview and SSH-forwarded thin clients. Therefore a native/main broker would be a new architecture, not existing trust; Electron process ownership cannot authenticate current socket requests or silently cover Preview/remote clients.

Verified current durable semantics: `web/src/server/durable/backend.ts` forwards client `clientSubmissionId` as host `requestId` and emits `session.submitAck` with that ID, `queued` and `submissionId`; `web/CONTRACT.md:532-534,1272` defines this as accepted submission/queue status, not consumption or guard clear. `pi/durable-host/run.ts:718-727` consumes `session-resumed`, clears the trip, then submits held inputs, but the event carries no visible ingress request/principal correlation. `core/src/session/resume.rs` checks the target blocked by loop guard and appends that event transactionally. `core/src/plan/archive.rs:337-353` shows agent refusal relies on caller-supplied `CPD_SESSION`/`CPD_ATTEMPT` environment markers (absent markers pass), not arbitrary-local-process authentication. `pi/lib/loop-guard.ts:116-129` classifies TUI input by `messageType === "user"`; this is input classification, not authenticated principal evidence. These are useful existing behaviors/hooks, not trusted WebUI ingress or proof of causal recovery.

Findings above are source inspection, not live security testing. Design assumptions/requirements remain explicitly provisional: a trusted boundary could authenticate a principal, authorize a target and bind an immutable request through an authoritative transition, but no current path proves this end-to-end. Status durability, same-user attacker assurance, ACL, credential lifecycle and correlation remain unresolved.

Ownership is split: engine-defects owns non-web `pi/lib`, `pi/durable-host`, `core/session`; this Job owns WebUI server/client authentication and acknowledgement. Proposed boundary is WebSocket upgrade authentication before hub creation, then server-derived principal passed in trusted server-side connection context (never accepted from client JSON); for each mutating request WebUI supplies immutable attached `sessionId`, `requestId`, and payload, while engine's non-web ingress receives principal/authorization context and returns a correlated authoritative outcome. Exact transport between WebUI server and engine is an open interface question: today's backend invokes `cpd session send` with `--origin webui` (`web/src/server/pi/backend.ts:35-40`) and that CLI surface does not currently convey authenticated principal; do not pretend that label is a trusted identity. Engine-defects must propose a trusted non-web handoff (typed API or authenticated internal invocation) and status lookup; no mechanism is selected.

Candidate request shape: `{principal: server-derived, sessionId, requestId, nonce, payloadDigest, operation, input}`. Candidate result: `{sessionId, requestId, status}` where statuses are `rejected`, `accepted`/`queued`, `held`, optionally `delivered`, `consumed`, `guard_cleared`, `failed`, `unknown`. This is a semantic sketch, not an implemented schema. One immutable chain `(requestId, principal-reference, targetSessionId, operation)` must flow through validation, enqueue, durable input and guard transition. A client-generated ID alone is not evidence downstream processed that request. Server validates target authorization for every operation, and engine revalidates target/principal at ingress and immediately before dispatch/clear. IDs are unique per principal; identical retries return original status; same ID with altered target/digest rejects. Persist deduplication/status for restart-safe queries if promised; expiry/privacy policy remains open.

Ownership per Lead addendum: engine-defects owns non-web `pi/lib`, `pi/durable-host`, `core/session` (trusted ingress, authorization/revalidation, dedup/status, consumption evidence and guard transition). This Job owns web server/client authentication and acknowledgement (credential boundary integration, correlation/UI, draft/attachment retention and query). Current `cpd session send --origin webui` cannot convey trusted identity merely through its surface marker; exact WebUI-to-engine trusted handoff must be designed jointly. No exact API/schema is selected.

Admission (`accepted`/`queued`) is acceptance/responsibility, not delivery, consumption, or recovery. `held` means deferred and trip remains; `rejected` means no admission; optional `delivered` is handoff, not consumption; `consumed` requires durable engine evidence of processing but does not prove guard clear; only authoritative correlated `guard_cleared` proves recovery. `failed` is terminal only if proven; `unknown` means commit/outcome uncertain. Pre-commit errors may be rejected; post-commit errors/disconnects are unknown until status query. Never auto-replay with a new ID or infer success. Retry only same ID/payload under engine's idempotent semantics after status lookup. Preserve draft and attachment bytes/IDs through disconnect/restart until definitive outcome; do not persist credentials with drafts. Define terminality, retention/privacy, unknown resolution and attachment encryption/persistence before implementation.

Guard state remains `blocked` until authoritative correlated `guard_cleared` for the bound target. Admission, `reply`, origin labels, attach, reconnect, `consumed`, or uncertainty cannot clear it. Recovery must be authenticated, authorized, target-revalidated and correlated; stale/mismatched/replayed intent rejects. Existing engine docs describe user prompt and `session-resumed` (§15.15); whether either can meet air-d137 assurance is unresolved. Separate explicit recovery-only action versus authenticated chat submission is a User decision.

## Facts versus decisions

Facts from inspected source: current WS accepts absent/`null`/`file://`/loopback origins and defaults to loopback; it has no credential check; connection attach resolves client-selected session and enforces subsequent ID equality, not principal authorization; `--origin webui` is a caller-surface marker. Current contract reports submission result at admission, not answer/consumption, and describes held UI/guard paths; those are existing engine semantics, not proof of authenticated human delivery. No code changed to implement or enable trust/recovery.

Decisions still required: OS/user-presence strength and local same-user attacker boundary; how Electron safely provisions bearer capability; Preview policy; exact trusted WebUI-to-engine identity handoff and interface; principal/session ACL policy; request/status persistence and expiry; what constitutes consumption; whether and how an authenticated human action clears guard; attachment persistence/encryption and restart behavior. Until approved and implemented end-to-end, no guard recovery and no mitigation claim.
