# WebUI trusted human ingress — proposed design (review required)

Status: design proposal only. No mitigation is implemented or enabled. This is not authorization to clear loop-guard state. Air-d137 requires authentication, session-target binding, and correlated delivery outcomes before WebUI loop-guard recovery; user review is required for unresolved security choices.

## Evidence and boundary

The inspected implementation has no authenticated principal: `web/src/server/ws.ts` accepts absent/`null`/`file://`/loopback Origin and defaults to loopback binding; Origin is not authentication and local non-browser clients can omit/forge it. `web/src/server/hub/connection.ts` resolves client-selected session IDs and enforces subsequent connection-to-session consistency (`not_attached`), but performs no principal-to-session authorization. `web/src/server/pi/backend.ts` adds `--origin webui`, a surface marker, not identity. `docs/contract.md` §§5.5, 6.13–6.15 and 15.15 document current input/delivery and guard behavior; notably `reply: true`/`cpd-chat` are not proof of a human. Scout evidence: `$CPD_HOME/run/desktop-shell/explore/webui-trust-scout.md` (transport Origin at `ws.ts:82-101,178-190`; attachment at `connection.ts:91-126`; contract unresolved at `docs/contract.md:4959,5269`). Scout is source inspection, not penetration testing.

Trust boundary should be the privileged host/engine, not renderer, browser Origin, labels, connection IDs, or caller-provided session IDs. All local clients—including malicious processes running as the same OS user, forged frames, compromised renderer/dependencies, replaying clients, and races across multiple clients—are adversarial. Loopback only reduces remote exposure; it does not isolate local callers. OS-user compromise or theft of a bearer credential defeats a same-user boundary. No claim of protection against these is made.

## Candidate authentication and lifecycle (unapproved)

Candidate: Electron main process obtains a high-entropy random per-launch bearer capability from a private local IPC boundary and passes it to the renderer without exposing it to page content; WebSocket upgrade presents it, server compares in constant time before constructing a hub/principal. Do not put it in URL, logs, Origin, local storage, or messages. Bind listener to loopback; rotate on host restart, revoke on renderer reload/logout/shutdown, expire with host lifetime, and fail closed if provisioning/validation fails. Avoid persistent credentials. This is a candidate, not a selected design: the exact IPC isolation, storage/permissions, hostile same-user process threat, browser Preview support, CSRF/cross-origin behavior, and whether OS user presence is required need User/Lead review. A random bearer proves possession by an authorized renderer channel, not a human at keyboard; if policy requires actual human presence, use explicit OS-mediated confirmation per recovery action instead. A process able to inspect/impersonate the same-user Electron process may steal the capability.

Authenticated principal must be server-derived and immutable per connection. Authorization must independently bind principal to an explicit target session and permitted operation; attach is not authorization. Bind each request to immutable session ID, connection/principal, unique request ID, and payload digest. Engine must reject mismatched target, duplicate IDs with different payload, stale/unknown principal, and replay; stable same-ID/same-payload retry returns the original outcome, never submits twice.

## Provisional exact boundary/interface (for cross-Plan reconciliation, not approved)

Lead addendum: `engine-defects` scout `scout-trusted-ingress-design-a1` is running with no candidate yet. Ownership is split: engine-defects owns non-web `pi/lib`, `pi/durable-host`, `core/session`; this Job owns WebUI server/client authentication and acknowledgement. Proposed boundary is WebSocket upgrade authentication before hub creation, then server-derived principal passed in trusted server-side connection context (never accepted from client JSON); for each mutating request WebUI supplies immutable attached `sessionId`, `requestId`, and payload, while engine's non-web ingress receives principal/authorization context and returns a correlated authoritative outcome. Exact transport between WebUI server and engine is an open interface question: today's backend invokes `cpd session send` with `--origin webui` (`web/src/server/pi/backend.ts:35-40`) and that CLI surface does not currently convey authenticated principal; do not pretend that label is a trusted identity. Engine-defects must propose a trusted non-web handoff (typed API or authenticated internal invocation) and status lookup; no mechanism is selected.

Candidate request shape: `{principal: server-derived, sessionId, requestId, payloadDigest, input}`. Candidate result: `{sessionId, requestId, status: held|rejected|admitted|consumed|unknown}` plus reason only where safe. This is a semantic sketch, not an implemented schema. Server validates target authorization for every operation, and engine revalidates target/principal at the trusted boundary. Request IDs are unique per principal; same ID + identical target/digest returns recorded status, same ID with different target/digest rejects. Persist deduplication/status long enough to cover reconnect/retry; expiry policy is open and must not silently permit duplicate delivery.

Engine owns credential-to-principal trust handoff validation, target authorization enforcement, durable deduplication, admission/consumption evidence, guard state/clear, and authoritative status. WebUI owns Electron-to-renderer credential handoff, WS authentication and per-connection principal, request correlation/ack presentation, local draft/attachment preservation, and reconnect/status polling. These ownership assignments are proposed for reconciliation, not evidence of existing behavior.

Admission is acceptance into a queue, not consumption by the agent. `held` means not admitted/consumed; `rejected` means definitively not accepted; `admitted` means accepted only; `consumed` requires engine evidence that the input was actually delivered/consumed according to the engine-owned contract. `unknown` means commit may have happened but outcome cannot be established; never auto-replay with a new ID or claim rejection. Before commit, errors may be rejected; after commit, errors/disconnects are unknown until querying the same ID resolves them. Disconnect preserves draft and attachment bytes and their stable IDs locally; reconnect queries status first, retries only same ID and exact payload when engine confirms not committed/rejected, and never silently drops or duplicates. Do not persist bearer tokens with drafts. Retention/expiry limits and encrypted attachment persistence require review.

Guard states: `blocked` remains blocked until engine's explicit authenticated clear transition for the bound target; WebUI receipt/queue admission, `reply`, origin labels, attach, reconnect, or an uncertain outcome cannot clear it. A clear request is distinct from input submission and must be authorized and correlated; stale/mismatched clear is rejected. On clear success report cleared only from authoritative engine result; failures/unknown remain blocked. Existing engine docs describe user prompt and `session-resumed` clear paths (§15.15); whether those qualify under air-d137 is unresolved, not presumed.

## Facts versus decisions

Facts from inspected source: current WS accepts absent/`null`/`file://`/loopback origins and defaults to loopback; it has no credential check; connection attach resolves client-selected session and enforces subsequent ID equality, not principal authorization; `--origin webui` is a caller-surface marker. Current contract reports submission result at admission, not answer/consumption, and describes held UI/guard paths; those are existing engine semantics, not proof of authenticated human delivery. No code changed to implement or enable trust/recovery.

Decisions still required: OS/user-presence strength and local same-user attacker boundary; how Electron safely provisions bearer capability; Preview policy; exact trusted WebUI-to-engine identity handoff and interface; principal/session ACL policy; request/status persistence and expiry; what constitutes consumption; whether and how an authenticated human action clears guard; attachment persistence/encryption and restart behavior. Until approved and implemented end-to-end, no guard recovery and no mitigation claim.
