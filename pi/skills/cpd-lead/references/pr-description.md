# PR description: the Lean template

## Why it exists

A PR body is for the reviewer and future readers, not for cpd's internal data. The diff shows what changed; the description explains why it exists, how the approach works, what trade-offs were made, and what was left for later. A reviewer reading the body should understand the intent, the design choice, and the proof that it works, all without reading cpd logs, Job keys, or SHA references.

## The Lean template

Use this template exactly, one line per section header, and omit any section with nothing to say. Write GFM only: no raw HTML, no footnotes.

```
## What and why

<problem and change in 2–4 sentences; start with the imperative>

## How

<approach, key decisions, trade-offs, shortcomings>

## Acceptance criteria

<checklist, each item checkable, each with its evidence>

## Out of scope and follow-ups

<what was deliberately left, naming registered Job and Workflow keys>

## Links

<ticket, design doc, sister pull requests, with inline context>
```

## Section rules

**What and why:** The problem and the change, in 2–4 sentences. Start with an imperative sentence (for example, "Validate user input in the /register endpoint. …"). A reviewer should understand the problem and the change in these two questions answered: what is broken or missing, and what does this PR do about it.

**How:** The approach, key decisions, trade-offs and shortcomings. Why this approach, not another. What was sacrificed. What is known to be rough. Enough that a reviewer can judge whether the change is sound and whether it fits the system.

**Acceptance criteria:** A checklist. Each item is checkable: it describes something testable (a test run, a command output, a manual observation) and ends with its evidence once known. A reviewer should see what was promised and what proved it. Examples: "`timeout 60 npm run build` succeeds"; "`npm run test -- test/auth.test.ts` passes"; "No regressions in the main app: verified by hand on the staging build at commit 62f4e9a".

**Out of scope and follow-ups:** What was deliberately left, naming registered Job and Workflow keys for follow-up work (for example, "Caching is not implemented; see Workflow cache"; "Error reporting for malformed tokens is a follow-up: Workflow error-reporting"). A reviewer reading this knows the boundary and can ask for what should have been done instead.

**Links:** Ticket, design doc, sister pull requests and other pull requests this depends on, with enough inline context that a dead link costs nothing. (For example: "Design: [Cache strategy](https://...); Blocks: PR shipping"; or "Fixes [#1234](https://...) (user login timeout)").

## Where the content comes from

Write the description from the Plan outline (`cpd plan show`), so nothing is written twice:

- **What and why:** from the Plan's `goal` and the decision round(s) the User approved.
- **How:** from the decision round(s) and the Job specs' `context` fields (what each Job needed to know about approach and trade-offs).
- **Acceptance criteria:** the checklist per Workflow in the `done_when` field, with the evidence filled in once the Jobs are done (the test runs and outputs).
- **Out of scope and follow-ups:** from the Plan's `out_of_scope` list and the `risks` that became registered follow-up Workflows and Jobs.
- **Links:** from the Plan's `decided` records (the Context decisions the Plan rests on) and from any stacked or dependent Workflows.

## Repo template rule

When the repo has `.github/pull_request_template.md`, fill that template instead of the Lean template. Fetch it with `git fetch origin`, then `git show origin/main:.github/pull_request_template.md`. Fill every section of the repo's template with the same intent (problem, approach, evidence, boundaries, links), keep its headings, and still carry all five ideas (what, why, how, acceptance, scope). The Lean template is the fallback when no repo template exists.

## Bad example

**Title:** Repo-declared exclusive resources for e2e runs

```
| Job | Status | Merged SHA |
|---|---|---|
| e2e-schema | Merged | a1b2c3d4 |
| e2e-tests | Merged | f5e6d7c8 |
| e2e-open | Merged | x9y8z7w6 |

Generated by cpd
```

**Why it is bad:** The body restates cpd's internal data (Job keys and SHAs). It tells the reviewer nothing of intent, approach or proof. A future reader cannot judge whether the change is sound without running cpd commands to fetch Job specs. The description is incomplete and makes the diff alone seem intentional rather than planned.

## Good example

**Title:** Cache query results to reduce database load

```
## What and why

Reduce database query count on the `/articles` endpoint by 70%. The endpoint queries the database for every request; with cache headers and Redis, we can serve most requests from cache and lower our database load from peak 300 qps to 100 qps.

## How

Use Redis with a 1-minute TTL for article list queries. Cache key is articles:<page>:<limit>. Invalidation: purge cache on POST /articles and PUT /articles/<id>. Trade-off: stale reads within 1 minute are acceptable; if consistency becomes critical, lower TTL or add purge events.

## Acceptance criteria

- [x] `npm run test -- test/cache.test.ts` passes (cache layer unit tests)
- [x] `npm run test -- test/articles.test.ts` passes (integration tests with cache)
- [x] `timeout 120 npm run load-test` shows mean latency under 50ms with 1000 requests (was 200ms)
- [x] Manual test: clear cache, load /articles, verify first request hits DB; second request is cached

## Out of scope and follow-ups

Cache invalidation for batch updates is not implemented; registered in backlog. Metrics and cache hit rate dashboard are future work; tracked separately.

## Links

Fixes [#432](https://github.com/.../issues/432) (database overload on peak traffic). Design doc: [Cache strategy for read-heavy endpoints](https://docs.internal/cache-strategy).
```

**Why it is good:** The body states the intent (reduce load), the approach (Redis with TTL and invalidation), the trade-offs (1-minute staleness), and the evidence (test passes, load test improvement, manual verification). A reviewer can judge whether the change is sound and complete. A future reader understands why the cache exists and can evaluate whether it still fits.
